# Run #2 Forensic Report — «переводчик заговорил сам с собой»

**Вердикт Run #2:** BLOCKED — SESSION/FEEDBACK LOOP. Задача: найти точный первый turn, где сломалось правило **1 committed source turn → 1 translation response**, и причинную цепочку. Модель/архитектура/VAD не менялись (жёсткое ограничение соблюдено).

## 1. Какие доказательства реально существуют

Экспорт Run #2 на тот момент содержал только `turns` / `sourceUtterances` / `cancellations` — **event-уровневого лога (response id, playback-состояние, таймстампы микрофона) не существовало**. Поэтому этот отчёт строго разделяет три уровня доказательности:

- **(A) Факты Run #2** — то, что видно в сохранившейся стенограмме/экспорте.
- **(B) Анализ кода** — что стенд/адаптер могли и не могли делать в принципе.
- **(C) Демонстрация анализатора** — синтетический Run #2-подобный лог в автотестах (`translatorForensics.test.ts`) показывает, что новая инструментовка *обнаружила бы* каждый из сценариев. Это проверка инструмента, **не доказательство** о самом Run #2.

Окончательное доказательство первопричины требует живого инструментированного прогона (Run #3) — он вне возможностей этой задачи (нужен реальный микрофон пользователя) и вынесен в follow-up.

## 2. Первый разрыв 1→1 (лучшая гипотеза по фактам A + B)

По стенограмме Run #2 последний «чистый» turn:

> 🎙 «После этого я не мог заснуть.» → “After that, I couldn't sleep.”

**Первый разрыв — следующий output “Hello.” без произнесённого источника.** Наиболее вероятный тип: `PLAYBACK_FEEDBACK_TURN` — VAD открыл новый входной turn, пока ещё звучал playback перевода. Гипотетическая цепочка:

1. TTS-перевод играет из динамиков → микрофон (browser echoCancellation слабо давит TTS-голос) слышит собственный вывод;
2. server VAD принимает его за новую речь → commit нового source turn;
3. модель, имея весь предыдущий рассказ в контексте и правило промпта «речь уже на выходном языке → повторить», продолжает рассказ по-английски (“I woke up at 3:30…”);
4. каждое продолжение снова играет → новые feedback-turn'ы → self-conversation loop;
5. шум/обрезки между эхо-кусками режутся на микротурны, где мультиязычный STT галлюцинирует японский/китайский/итальянский (симптом петли, не причина).

До Run #3 это остаётся **обоснованной гипотезой**, а не доказанным фактом: точный `item_id` первого сломанного turn'а из Run #2 восстановить невозможно.

## 4. Итог по причинной цепочке

Единственная гипотеза, объясняющая ВСЕ факты Run #2 разом (самопродолжающийся рассказ + мультиязычные микротурны + серия cancellations): **акустическая петля playback→микрофон**, при которой VAD-тюнинг ничего не решает — разрыв происходит до VAD, на уровне негейтированного входа во время playback. Подтверждение/опровержение — на первом же живом прогоне: экспорт теперь включает полный event-log и автоматический forensics-вердикт.

## 5. Что добавлено (инструментовка, без изменения модели/VAD)

- **Полный event-log стенда**: каждый provider-event + `mic_audio`/`playback_start`/`playback_end`, все со `seq`, `ts`, `playbackActive`; `speech_started` несёт флаг `playbackActiveAtSpeechStart` («output ещё играл, когда пришёл следующий speech_started» из спеки); audio-события несут `responseId` до самого браузерного лога. Экспортируется в JSON-отчёт целиком.
- **Живые инварианты в адаптере** (`invariant_violation`): `RESPONSE_WITHOUT_SOURCE_TURN`, `MULTIPLE_RESPONSES_FOR_TURN`, `OUTPUT_AFTER_RESPONSE_DONE` (deltas И terminal transcript.done); события `input_committed`/`response_created`; `responseId` во всех output-событиях.
- **Feedback-детектор**: source turn, чей VAD-старт пришёлся на активный playback, помечается `suspectedFeedback` (⚠ в ленте, счётчик в scorecard) — нарушение «translation response не должен порождать новый source turn».
- **Fail-closed анализатор** `server/translation/forensics.ts` (+ dev-endpoint `/translator-spike/analyze`): PROVEN/DISPROVEN/INCONCLUSIVE по всем 5 подозрениям; DISPROVEN выдаётся только при полной атрибуции (каждый response привязан к committed item, ≤1 response на item, все output-события с response id) — неполный/повреждённый лог никогда не экспортируется как «чистый». Усечение лога (браузерный cap или cap endpoint'а) всегда СЧИТАЕТСЯ и помечает анализ `truncated`: все вердикты становятся INCONCLUSIVE и первый 1→1-разрыв не заявляется по частичным данным.
- **Автотесты** `translatorForensics.test.ts` + `translatorRelay.test.ts`: инварианты адаптера, сохранение `responseId` через WS-relay, fail-closed пути анализатора, Run #2-подобный сценарий (демонстрация обнаружимости) и чистый лог.
