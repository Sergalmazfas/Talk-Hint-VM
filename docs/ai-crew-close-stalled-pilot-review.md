# Owner-only: закрыть зависший Hint-пилот

## Назначение и границы

Дополнение к принятому Клавдием исправлению диспетчера/jsonb-хэша. Код готовится
в Dev; никаких обращений к production, включений, повторных пилотов или платных
запросов. Все тесты — с fake provider; PostgreSQL — только Dev TEMP-фикстуры.
Publish выполняет владелец после независимой проверки этого пакета.

## Контракт

Закрытая панель `/admin/ai-crew`, кнопка «Закрыть зависший пилот».
Используется прежний owner endpoint `/api/admin/ai-crew/command`:

```json
{
  "revision": 123,
  "command": {
    "kind": "hint_pilot_close_stalled",
    "taskId": "UUID текущего пилота",
    "ownerApproved": true
  }
}
```

Те же вход владельца, Origin, CSRF и транзакционный CAS. Никаких новых
интеграционных полномочий, API-ключей или обхода owner-auth.

### Условия, повторно проверяемые сервером под блокировкой строки

- Глобальный переключатель строго OFF.
- Задача принадлежит текущему владельцу, Hint-пилот author, analysis, не закрыта.
- Есть queued-запуск; все её запуски только queued/discarded.
- Нет running/unknown/done, положительного или неизвестного резерва,
  уже учтённой стоимости/использования токенов, документов, proposal/review.
- Общий журнал бюджета не содержит незакрытых резервов, включая прошлые дни.
  Это консервативный отказ: общий резерв без надёжной атрибуции не освобождается.
- Повторное закрытие, несуществующая/чужая задача и неподтверждённая команда —
  отказ без изменений.

### Одна транзакция, одна новая revision

1. Каждый queued становится discarded, cost=0, completedAt=дата действия.
2. Задача: closed=true, phase=outcome, Hint-status=not_completed.
3. Добавляется итоговый шаг владельца с actual/note
   «не выполнено: зависание диспетчера», met=false. Это не успешная приёмка,
   не положительный лабораторный итог и не имитация owner expectation.
4. OFF сохраняется; дневной лимит становится 0, epoch увеличивается.
   Причина: обычная подготовка нового пилота требует OFF/0.
   В подтверждении прямо сказано, что лимит станет 0.
5. Записи run_discarded_without_execution на каждый запуск и
   hint_pilot_closed_stalled: кто, когда, taskId, IDs очереди, итог, costMicroUsd=0,
   прежний/новый лимит, enabled=false, agentsStarted=false.

Бюджет spent/reserved не переписывается, строки/документы/старая история
не удаляются. Уже существующие расходы не превращаются в нулевые.
При завершении полноценной цепочки Паша → Фома прежнее правило сохраняется:
автоматический OFF НЕ обнуляет дневной лимит. Сброс здесь — только явное
подтверждённое закрытие владельцем неисполненной задачи.

## UI

- Подтверждение «Вы уверены?» с итогом, сохранением истории и сбросом лимита.
- Свежий GET → CSRF/revision → повторная проверка → один POST → новый GET.
- Readback сверяет ровно +1 revision, закрытую задачу, итог, discarded/cost=0,
  OFF/0 и запись журнала.
- Ошибка, неясная квитанция или несовпадение — STOP без повторного POST,
  блокировка новых пилотных действий до ручного чтения.
- Отмена подтверждения и отказ свежего состояния — никакого POST.
- Никакого автозапуска: после закрытия доступна новая подготовка, затем
  отдельные подтверждения включения и запуска.

## Проверки

- Domain: положительное закрытие, сохранение предыдущих шагов/журнала/расходов,
  все опасные статусы, резервы текущего/прошлого дня, стоимость/usage,
  чужой владелец, повтор/отсутствующая задача.
- Runtime с fake provider: close и новая prepare/enable не вызывают модель;
  только отдельный start нового UUID создаёт исполнение; старая очередь discarded.
- HTTP: owner + Origin + CSRF + CAS; отказы сохраняют состояние, никаких
  моделей/list/probe, повторное чтение подтверждает одну revision.
- PostgreSQL: настоящий CrewStore и jsonb в connection-local TEMP-таблице Dev;
  unsafe rollback, stale CAS, атомарное сохранение и чтение.
- UI: настоящий inline JS, fake DOM/HTTP/confirm; свежий CSRF/revision,
  running/unknown/резервы/OFF, отмена, ошибка/неясность/расхождение без повтора,
  полный цикл закрыть → подготовить → включить → запустить по четырём кликам.
- Полный набор — последовательно четырьмя шардами, ничего не отключать ради зелёного.

## После независимой сверки и Publish владельцем

На https://talkhint.app/admin/ai-crew владелец обновляет состояние, убеждается в OFF
и допустимости закрытия, нажимает новую кнопку и подтверждает действие.
После подтверждённого чтения OFF/0 и failed outcome выполняет обычные отдельные
шаги: «Подготовить пилот: задержки» → «Включить с лимитом» → «Запустить пилот».
Сам Publish и открытие страницы не закрывают и не запускают задачу.
Не ставить Copy development database to production.

Не проверены: реальный owner click и платный production-пилот, будущие реальные
токены/цена, signed-in визуальный экран (Screenshot без входа видит auth gate).
Катя, звонки, промпты, модели, сотрудники, iOS и схема БД не меняются.
