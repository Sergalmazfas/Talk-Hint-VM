# Hint latency: зависание queued до резервирования

## Границы

Production: только чтение deployment-телеметрии. Никаких POST, SQL к production,
перезапусков, повторных запусков, изменения OFF/лимита/задачи или платных запросов.
Dev-тесты используют fake provider и connection-local TEMP-таблицы PostgreSQL.
Владелец уже нажал аварийный OFF. Текущее состояние OFF не подтверждено owner API:
у Replit нет сессии владельца; не обходить защиту.

## Причина и степень доказанности

`evidenceHash` раньше использовал `JSON.stringify` исходного объекта. PostgreSQL
jsonb меняет порядок ключей. После первого сохранения тот же смысловой снимок
с другим порядком ключей не проходит `pilotInput`: `EVIDENCE_CHANGED`.
Это происходит внутри транзакции до `run_reserved`, платного запроса и расходов.
Транзакция откатывается, queued остаётся; следующий интервал видит то же состояние.
Внешний catch глушил ошибку. Такой дефект детерминированно воспроизведён через
настоящий PostgreSQL; после исправления тот же тест проходит.

Это доказанный дефект кода, полностью объясняющий указанный симптом. Исключение
именно production-запуска в логах не зафиксировано, поскольку старый catch пуст.
Не выдавать реконструкцию за найденную строку production-лога.

## Разбор четырёх подозрений

- Интервал: production-ветка `registerCrewRoutes` устанавливает 15-секундный
  interval; вызов регистрации есть в `server/routes.ts`. Проверено таймерами.
  Исполнение этого интервала в старой опубликованной сборке не было залогировано.
- deployment()/tick: до tick есть запись наблюдения публикации. Любое исключение
  блокирует текущую попытку. Новый лог различает `publication` и `tick`, но
  не меняет fail-closed и не обходит журнал публикации.
- busy/ticking: оба сбрасываются в finally при исключении. Тесты это проверяют.
  Реально незавершённый Promise не разблокируется насильно: иначе возможен
  параллельный платный запуск. Через минуту логируется dispatcher_busy.
- pilotInput/резерв: jsonb/hash ломает pilotInput до расчёта резерва. Отдельно
  лимит 5 microUSD недостаточен и тоже оставляет queued без запроса. Добавлен
  `run_budget_blocked` с числовыми резервом/лимитом/расходом, без выдержки.
  Установленный владельцем лимит и цена production здесь не считаны.

## Исправление

1. Канонизация порядка полей по исходной проекции v1: старые подготовленные
   хэши остаются валидны. Массивы не сортируются, значения не меняются;
   лишние поля сохраняются и участвуют в хэше, удаление/подмена не маскируются.
2. Диспетчер вынесен в тестируемый helper. Только production, те же 15 секунд,
   тот же порядок publication → tick, busy/finally, unref.
3. Логи: dispatcher_started, первый dispatcher_tick_ok, dispatcher_failed
   (фаза + allowlist кода), dispatcher_busy; без error.message/stack/input/key.
   Неизвестные ошибки получают DISPATCH_FAILED. Платные unknown не повторяются.
4. Нижний бюджет microUSD — только чтение. Save сохраняет лимит из свежего GET,
   с актуальным CSRF/revision и подтверждением; меняет срок и выключает контроль.
   Поле долларов пилота остаётся: 5 = $5, а не 5 microUSD.

## После проверки Клавдия и Publish владельцем

- Никакого кода автозапуска/сброса/миграции состояния нет. Publish не включает Crew.
- Владелец сначала читает https://talkhint.app/admin/ai-crew и проверяет OFF,
  лимит и очередь. Запуск — только его отдельным действием.
- Важное ограничение: аварийный OFF не переводит старый author/queued в prepared.
  Текущие кнопки enable/start принимают только prepared; новая подготовка
  запрещена при незакрытом пилоте. Этот патч намеренно не сбрасывает старую задачу
  и не добавляет скрытый повтор. Для старой queued-задачи нужен отдельно
  согласованный безопасный owner-путь возобновления. Нельзя обещать, что её
  можно запустить повторно стандартными тремя кнопками без этого шага.
- После явного owner-запуска проверять run_reserved → Паша → Фома → OFF,
  лимит не менять. При unknown/ошибке не повторять. При >5 минут аварийный OFF.
- Публикация не меняет iPhone-приложение; в этом пакете iOS-правок нет.

## Не проверено

Реальное выполнение пилота, токены/цена, состояние owner API и signed-in UI,
будущие production-логи новой диагностики, причина конкретного обращения в старом
production-процессе напрямую (ошибки не логировались). Production не перезапускался.
