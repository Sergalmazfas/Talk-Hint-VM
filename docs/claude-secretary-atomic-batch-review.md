# На сверку Claude: атомарное создание отдела Секретаря

## Задача и границы

Исправить отказ `create_secretary_department_structure` при сохранении
фиксированного пакета. Только Dev; Publish выполняет владелец после сверки.
Production MCP в этой работе не вызывался, данные production не менялись.
Новые агенты, задачи, расписания, голоса, личности, рабочие промпты,
телефонные назначения и iOS не изменяются.

Последняя ранее подтверждённая production-ревизия — r1011:
Мария и продуктовые принимающие P-BENCH перенесены; отдел не создан.
Это историческая контрольная точка, не новое чтение production.

## Причина

Фиксированный инструмент создаёт шесть команд модели: граф, три анкеты,
документ каталога и связь существующей Кати с руководителем. С квитанцией
получается семь. Реальные репозитории ограничивали пакет тремя командами.
Независимый ограничитель v3 также разрешал продвижение ревизии только на 1–3.
Старые тесты отдела использовали in-memory repository без этих ограничителей.

## Исправление

- Общий лимит остаётся 1–3 команды и 1–3 шага ревизии.
- Только фиксированный production-инструмент после формирования квитанции
  отмечает точный семикомандный пакет серверным разрешением в памяти процесса.
- Проверяются форма пакета, ожидаемые ID документов и непринятая квитанция.
- Разрешение привязано к объекту массива, владельцу, исходной ревизии
  и хэшу всего пакета; допустима только модель `new-country`.
- JSON, копирование массива, изменение вложенных данных, другой владелец,
  другая ревизия или workspace разрешение не переносят.
- Все три типа репозитория применяют один ограничитель.
- v3 передаёт разрешение только своей конкретной функции подготовки дельты.
  Для неё допустимо ровно +7 ревизий; общий предел не повышен.
- Всё сохраняется одной существующей транзакцией. SQL-схема и публичные
  схемы команд/MCP не меняются; новый универсальный инструмент не добавлен.
- Проверки владельца, закрытой записи и CAS остаются на прежних местах.

## Проверки и их пределы

Новые регрессии:

1. Настоящие методы PgModelRepository, CompanyModelRepository,
   CommandCompanyRepository.writeMany и updateMany допускают пакет сервиса.
2. Те же методы отклоняют неавторизованные большие пакеты до хранилища.
3. Сохранены общие пределы; проверены чужой владелец, неверная ревизия,
   другой workspace, JSON-копия и мутации после разрешения.
4. Проверены отдельное разрешение подготовки дельты и продвижение ревизии.
5. Настоящий IncrementalCompanyRepository.commitDelta проходит SQL-путь
   BEGIN → проекции → revision/document heads → CAS → COMMIT на изолированных
   SQL/frame doubles. При ошибке flush, третьего документа или CAS — ROLLBACK,
   без изменения зафиксированного состояния.
6. Сохраняются отказы при закрытой записи и устаревшей ревизии.

Это НЕ прогон на физическом PostgreSQL и НЕ production-запись.
SQL/frame doubles проверяют порядок и атомарный отказ, не PostgreSQL constraints
или полную реляционную проекцию большого production-снимка.
Прежние тесты отдела дополнительно проверяют содержимое, чтение, дедупликацию
и proposed-имена. Их подменённый repository сам по себе не служит
доказательством совместимости с реальными ограничителями.

TypeScript проверяется `npm run check`; тесты —
`npm test -- --maxWorkers=1`. Результаты приложены отдельно.
Dev workflow перезапущен один раз и запущен; `/admin/team` сохраняет вход
владельца. Signed-in UI не проверялся визуально; UI-код не менялся.

## Что проверить Claude

- Нельзя ли перенести разрешение на посторонний пакет, владельца или ревизию?
- Не повышены ли обычные лимиты команд и ревизий?
- Не разрывается ли разрешение при проходе production repository → v3?
- Доходит ли весь пакет с квитанцией до единственного COMMIT?
- Сохранились ли защита закрытой записи, CAS и отказ без частичного отдела?
