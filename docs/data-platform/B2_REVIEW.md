# B2 — инкрементальная запись, только кандидат

## Граница

Принятый B и старый JSON остаются неизменными. Полноразмерные нагрузочные копии
имеют собственные owner/workspace и явные метки `B2 … NOT shadow B`.
Первый прогон сохранён; после исправления смешанных команд создана новая
полная копия для финального прогона. Обе **не активны** и сохраняются до ручного
прохода владельца. Production, Hint worker, QA, письма и дежурный не включались,
не выключались и не перенастраивались.

## Что изменено

1. Типизированные бизнес-таблицы содержат неизменяемые версии записей с
   content digest. Членство в ревизии, порядок и форма исходных объектов
   отделены от содержимого записи. Stable ID остаётся исходным ID, не digest
   и не индексом массива.
2. Форма объекта задаётся общим версионированным контрактом полей; его значения —
   ссылки на типизированные колонки или типизированные вспомогательные значения.
   Контракты полей не копируются для каждой новой ревизии. Отсутствующее поле,
   null, пустые массив/объект, числовые ключи и порядок массивов различаются.
3. Исторические массивы — неизменяемые деревья ссылок. Вставка первой ревизии
   operatingModel не меняет адреса прежних записей и графов.
4. Длинные строки, включая before/after/strategyChange, хранятся как
   SHA-256-снимки с точным текстом. И аудит, и бизнес-колонки ссылаются на
   один пул строк. Объектные снимки составлены из неизменяемых записей/ссылок,
   не из нового монолитного JSON. Сжатие с потерями не применяется.
5. Бизнес-контракт декодирования зафиксирован отдельно от живой SQL-схемы.
   Неизвестная версия/неверный digest останавливают чтение. Нормализацию
   старого контракта нельзя молча менять.
6. В обычной транзакции проверяются вставленные строки (`INSERT RETURNING`),
   владельческий scope, CAS и целостность изменённых данных; нет `readRoot`,
   полной `project(next)` и проверки всего workspace.

## Важное уточнение стоимости

Для совместимости используется тот же чистый доменный движок. Он получает
рабочий набор выбранной гипотезы, без старых решений и без всех старых графов;
для saveOperatingModel подаётся последняя ревизия и новый граф. Валидация
текущего рабочего набора остаётся, то есть это не обещание O(1) для любого
доменно сложного запроса.

`writeMany` возвращает квитанцию инкрементальной записи. Старый контракт
`updateMany` обещает полную гипотезу и потому после commit выполняет отдельное
полное чтение для ответа. Это **не** проверка writer. Эта стоимость не скрыта:
в нагрузочном отчёте полные чтение/сверка и проверка истории измерены отдельно.
Оптимизация полного ответа книги — отдельный следующий шаг, не смена её контракта.

Прямой reader документа и `get_document` не разворачивают весь workspace.
Чтение привязано к owner/environment/revision; повреждение не ведёт к
молчаливой подстановке legacy.

## Исправление после финального прохода кода

Первый вариант пропускал изменение старой записи, если в том же пакете
добавлялась новая запись того же массива. Теперь сохранение тела записи и
изменение состава/порядка массива проверяются независимо. Неизменённые
записи сохраняют прежние frame-ссылки, включая перестановки.

Также у добавленного документа индекс раньше мог указывать на весь массив,
а не на сам документ. Теперь head всегда получает frame элемента до вставки
в массив. Новые audit-поля с `undefined` проходят ту же JSON-границу, что
старое хранилище (поле отсутствует, не null); старые снимки не пересериализуются.

Регрессия: четыре смешанных SQL-пакета (update→append, append→update,
update→append→update той же записи, два update→append). Полный результат
сравнивается с последовательными прежними доменными командами; дополнительно
проверяются прежняя ревизия, прямой reader и get_document каждого документа.
Проверки структурных массивов охватывают все пять семейств entity-массивов,
рост/сокращение/перестановку и повторное использование неизменённых frames.

## Подготовка production

`OwnerImportService` — подготовленная служба, **без установленного HTTP endpoint**.
Требует серверного owner session/CSRF-контекста; auth нельзя брать из тела запроса.
Разрешение связано с source owner/environment, target owner/environment,
digest манифеста, сроком и одноразовым токеном. Целевой owner ещё предстоит
подтвердить владельцу.

После Publish №1 будущий обработчик должен получить owner-сессию, проверить
подтверждённую привязку аккаунтов и передать поток записей в утверждённом порядке:
business contract/контракты; legacy root/history; снимки; бизнес-записи;
text refs; frames; heads/индексы/размеры/archive refs. Передача большого
архива — потоком, не единым массивом. JSONB используется для транспортной
десериализации строки SQL, не как хранилище нового монолита модели.

В одной транзакции: блокировка цели → повторная проверка пустоты → импорт →
digest/count потока → полное чтение/semantic SHA → прямые индексы документов →
порционная проверка архивов → commit. Неактивный shadow — по умолчанию.
Явное включение после этой проверки возможно только отдельным owner-действием;
в B2 ни один источник не включён. Production запрещён по умолчанию и не
проверялся фактическим переносом. Реальный production grant не создавался.

Синтетическая проверка проверяет двух конкурентных импортёров, подмену потока,
неверные scope/CSRF, истечение, повтор токена, точный перенос архивного payload
с привязкой к новому owner и отсутствие включения.

## Как читать цифры

- `semanticHash` — SHA канонического полного JSON; он сравнивается с прежним
  движком. Структурный `rootHash` — другой digest формата хранения, не подмена SHA.
- Новые UUID и часы независимых запусков доменного движка нормализованы перед
  сравнением. Содержательные поля не копируются из проверяемого результата.
- `delta.*.logicalBytes` — байты JSON-транспорта вставленных строк, не объём диска.
- `inventory.*.tupleBytes` — SQL `pg_column_size` выбранных строк workspace.
- Физический размер таблиц включает индексы/TOAST/свободные и старые страницы
  **всех** workspace этой таблицы. Физический объём всей Dev-базы берётся
  отдельно через `pg_database_size`; в нём остаётся B и остальные системы.
- Сумма строк workspace в сыром нагрузочном отчёте исключает одну строку
  реестра workspace и общие словари контрактов. README показывает этот scope
  явно. Это не счёт всех строк звонков/сессий/остальных таблиц проекта.

## Чего этот пакет не подтверждает

Нет Publish, production import, реальной привязки аккаунтов, переключения
источника, подписанной UI-проверки web-книги или включения новых агентов.
Сохранены согласованные ограничения размера активных данных в символах:
это не PostgreSQL row limit. Срок заполнения из числа SQL-строк не выводится.
Проверка на 20 правках не доказывает поведение после тысяч будущих ревизий.

## Восстановление и удаление

Неактивный кандидат не требует rollback продукта: активный legacy и B не
изменялись. Все новые и предыдущие heads в копии сохранены. Архивные payload
не удалялись; 242 ссылки проверяются по исходным digest.

Автоматического удаления полноразмерной копии нет. Будущее удаление — только
после ручной проверки владельца, по workspace ID из RETAINED_WORKSPACE.json
и списку FINAL_VERIFICATION/нагрузочного инвентаря. Никаких wildcard по
`company-*`, удалений shared contracts, legacy или принятого B.
