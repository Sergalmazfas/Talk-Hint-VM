# Платформа данных TalkHint — решение владельца 28.10.2026

Статус: целевая схема согласована владельцем; этап 0 подготовлен в Dev.
Этапы 1–7 пока не выполняются. Каждый этап: diff → тесты → сверка
количеств, стабильных ID и контрольных сумм → «да» владельца → Publish владельцем.
Ни новая инфраструктура, ни подготовленный код сами по себе не являются приёмкой.
Ответственный за техническое исполнение — HEAD.07; эксплуатация — P.OPS;
содержание паспорта и журналов — P.PRODUCT; сохранность контура Hint — P.LAB.

## 0. Срочное освобождение рабочего пространства

- Только `new-country`: 5 000 000 → 6 500 000 единиц UTF-16 сериализованного
  рабочего набора. Исходная гипотеза остаётся на 5 млн, общий конверт — 8 млн.
- Один документ — прежний ID и полный `text`. До 50 000 единиц хранится как прежде.
  Более длинный текст хранится неизменяемыми томами до 50 000 в уже существующем
  owner-scoped архиве PostgreSQL. Предел полного текста на переходный период —
  500 000 единиц. Том не является новым документом или вторым каталогом.
- У томов — адреса по digest, порядок и контрольная сумма полного текста.
  Обычные `get_document`, web-книга и JSON получают собранный полный текст.
  `get_document` дополнительно сообщает манифест томов длинного документа.
  Исходные JSON-документы не режутся на независимые JSON-фрагменты.
- Неполный/повреждённый/чужой архив — ошибка, а не пустой документ.
- Тома не уменьшают логическую меру активного набора: это временное решение
  ограничения одного документа, не подмена результатов CAP-аудита.
- Нет массовой перезаписи, новых таблиц, DDL, вызовов моделей, писем, включения
  новых агентов или изменений Hint. Подготовка меняет только Dev-код.
- До первого сохранения длинного документа старое хранение совместимо.
  После него откат на код без сборщика томов недопустим: оставляем новый reader,
  откатываем только прикладные изменения. Старый JSON/архив не удаляется.

## 1. Схема нормализованной модели — предложение до начала переноса

Во всех ключах `workspace_id` и `hypothesis_id`; владелец выводится из
проверенного серверного доступа, не из произвольного параметра клиента.
Стабильные бизнес-ID сохраняются как `text`, не заменяются случайными UUID.
Технические события и задания могут иметь собственные UUID.
Все внешние ключи содержат область модели; одинаковый ID другого владельца
не даёт доступа. Нельзя связывать строки разных моделей или окружений.

Предлагаемые таблицы (префикс `company_`, окончательный DDL — только на этапе 1):

| Таблица | Содержимое / ключевые ограничения |
|---|---|
| workspaces | Привязка владельца к существующей модели; текущее поколение хранения, CAS revision, выбранная гипотеза |
| hypotheses | Исходная и new-country, стабильные ID и метаданные |
| entities | Реестр ID и типа всех нынешних узлов/legacy elements; уникальность ID внутри соответствующего namespace |
| roles | Паспорта ролей, подчинение, ссылки на контролёров; FK в entities |
| actions | Вход, результат, исполнитель, принимающий, частота, критерии; FK в entities/roles |
| resources | Существующие ресурсы и честный статус выдачи, владелец; не секреты |
| nodes | Прочие типы узлов без потери полей и исходного типа |
| links | Прежний ID, endpoints, тип/смысл и свойства; FK в entities, индексы по обоим концам |
| documents | Прежний ID, название, текущая версия, связи с узлами |
| document_versions | Неизменяемый полный текст/тома, revision, SHA-256, автор, источник; unique(document,version) |
| document_entity_links | Связи документа с прежними элементами, не потерять legacy elementIds |
| model_revisions / entity_versions | Событие изменения и неизменяемые версии объектов, source revision, digest |
| legacy_archives / import_manifests | Неизменяемый указатель на прежний JSON/архив, hash, источник, результаты сверки |
| extensions | Только не вошедшие в явную схему дополнительные поля с namespace и версией; не свалка всей модели |

Удобные названия здесь сокращены; фактический префикс применяется ко всем таблицам.
Реестр namespaces отличает legacy elements от operating nodes: ID не переименовывать
ради возможной коллизии. Таблицы и внешние ключи проектируются по полному инвентарю.
У каждой таблицы контракт версии, `created_at`, происхождение и аудит изменения.
Изменяемые поля — колонки с типами/ограничениями; расширяемые свойства — ограниченный
JSONB. Нельзя перенести монолит в одну новую JSONB-колонку и назвать это нормализацией.

### Чтение и запись без остановки Hint

1. Добавить таблицы в `shared/schema.ts`, применить и проверить только Dev.
2. Read-only инвентарь всех полей, типов, ID, ссылок, версий и существующих таблиц.
3. Пакетный повторяемый импорт **снимка Dev** с source revision и manifest;
   нормализованные данные пока не источник операционных записей.
4. Сверить количества по типу, наборы ID, каждую ссылку, тексты, версии и hashes.
   Кроме семантических digest — точный digest исходного сохранённого текста.
5. Теневое чтение того же ModelRepository → то же публичное представление.
   Сравнить книгу, главы, get_document, get_team, roadmap, поиск и полный JSON.
6. Довести изменения после исходной revision до одной контрольной точки.
   Короткий CAS/barrier затрагивает только записи модели, не звонки или worker.
   При несовпадении повторить импорт/дельту; не затирать изменения.
7. Переключить источник **одной атомарной операцией** по workspace.
   После переключения JSON — неизменяемый архив; не dual-write и не вторая истина.
   Старый JSON реконструируется для экспортов из нормализованного источника.
8. Новые изменения имеют нормализованные версии и аудит. Ошибка переноса
   не отключает call_lab/outbox/телефонный контур.

Production: схему переносит штатный Publish Replit; никаких production DDL
в старте, build или самодельном скрипте. Publish **не переносит строки Dev**.
Для данных production до переключения нужен отдельный согласованный механизм
backfill через защищённую доменную операцию в её собственной базе, read-only
источник, CAS и такой же manifest; не импортировать туда Dev-звонки и настройки.
До его готовности production использует прежний адаптер. Не обещать автоматическую
миграцию данных одной публикацией.

### Откат

До переключения — выключить теневое чтение, существующий источник остаётся.
После новых нормализованных записей нельзя просто указать на старый снимок:
он отстал. Откат — совместимый reader/исправление вперёд или сверенный обратный
экспорт всех новых изменений; нужен отдельный план и контрольная точка.
Архив не удаляется, независимо от выбранного пути.

## 2. Журнал, документы, решения и отчёты

- `journal_cases`, `journal_events`, `issue_attempts`: одна проблема, история
  попыток именно этой проблемы, решение, проверка, оценка владельца.
- `decisions`, `decision_lines`, `acceptances`: автор, полномочие, статус,
  входная версия, причины отказа; молчание не приёмка.
- `reports`, `report_metrics`, `report_links`: версионированный результат и
  вычисленные кодом числа отдельно от AI-интерпретации.
- Не создавать второй реестр звонков: использовать существующие `calls`,
  `call_lab_jobs`, outbox и журналы выполнения после инвентаря фактических FK.
- Текущие текстовые документы остаются доступны со стабильными ID как
  версионированные представления новых строк; прежние версии не пересобираются
  с сегодняшними формулировками. Все исходные JSON сохраняются в архиве.
- Валидация схемы каждого пакета, ссылки и публичные контракты проверяются
  вместе, прежде чем разрешить запись в новый источник.

## 3. Файлы — Replit App Storage

`file_assets`: прежний ID, владелец, режим, `object_key`, SHA-256 исходных байтов,
тип, длина, версия, происхождение, статус загрузки. Большие снимки, результаты
стендов, экраны, видео, портреты, аудио — объекты, не base64 в модели.
Запись: upload → проверка байтов/digest → транзакционная ссылка. Незавершённое
не считать готовым. Повторяемый upload по manifest, без удаления исходников.

App Storage проекта доступно и Dev, и production: **это не изоляция окружений**.
Нужны отдельные закрытые buckets, если доступны, и обязательные env/owner prefixes
и серверная проверка доступа. Нельзя выдавать постоянные публичные URL для звонков.
Точные способы скачивания/истечения доступа проверяются с SDK на этапе 3.
Web/MCP/экспорт продолжают выдавать содержимое или авторизованное получение,
а не бесполезный набор закрытых ссылок.
Перенос уже согласованных аудио не разрешает новые записи или обход согласий.

## 4. Память команды — pgvector в той же PostgreSQL

В Dev PostgreSQL 16.10 доступно расширение vector 0.8.0; пока не установлено.
Production поддержка расширения должна быть отдельно проверена до её применения.
`memory_items`, `memory_versions`, `memory_embeddings`:
owner/env/role/mode, стабильный ID источника, source version/digest, дата урока,
разрешённая область, embedding model/dimension, статус свежести.

Память — поисковый индекс канонических уроков/истории, **не новый источник истины**.
Исправление источника инвалидирует embedding; поиск всегда возвращает источник
и дату. Фильтр owner/env/доступа применяется в SQL до выдачи результатов.
Выбор embedding-модели, размерности и индекса (HNSW/точный) — по стенду и
отдельному решению по использованию существующего ключа. Никакого неразрешённого
вызова модели или расхода сейчас. Бюджет генерации embeddings — отдельно.

## 5. Разделение Dev / production

Обе базы уже существуют отдельно: read-only проверка 28.10 видит PostgreSQL
16.10 в Dev и 16.15 в production, по 42 public-таблицы в каждой.
Версия/число таблиц — только свидетельство подключений, не равенство данных.

Контроль разделения нужен **уже на этапе 1**, а не впервые на этапе 5.
Этап 5 завершает сквозные тесты: маршрутизация соединений, запрет перекрёстного
доступа, отдельные очереди, storage namespaces, бэкапы, ключи/доступы.
Не создавать третью базу без необходимости и не копировать production в Dev.
Агенты не получают произвольные SQL credentials; только выданные инструменты.

## Очередь агентов

На этапе 1 инвентаризировать уже работающую SQL-очередь `call_lab_jobs`.
Её не заменять во время переноса модели. Для новых типов — совместимый
`agent_jobs` либо расширение существующего механизма после проверки:
idempotency_key, источник/версия, роль, статус, attempts, lease/heartbeat,
not_before, result_id, error, timestamps. Захват `FOR UPDATE SKIP LOCKED`,
короткая транзакция, ограниченные повторы и dead-letter.
Доставка at-least-once, идемпотентный результат; отправка почты через outbox,
не обещание невозможного exactly-once внешнего API.
Включение новых исполнителей — отдельное «да», не следствие наличия таблицы.

## 6. Резервные копии и восстановление

Replit предлагает ежедневные production backup и PITR; окно зависит от плана.
Это не доказательство, что расписание уже включено в этом проекте.
На этапе 6 проверить настройки, согласовать окно хранения и включение;
не выбирать срок хранения бизнес-данных без владельца.
Dev checkpoint — не замена независимой ежедневной проверяемой резервной копии.

Backup manifest: окружение, время snapshot, schema version, model revision,
количества, ID-set hashes, document/file digests, status, проверка полноты.
Для App Storage — отдельное покрытие объектов: резервная копия PostgreSQL
не копирует байты видео/аудио. Не обещать восстановление файла по одной ссылке.
Ежедневная копия + проверка восстановления в изолированной временной Dev-схеме/
тестовой базе (никогда поверх рабочих таблиц), сравнение manifest и удаление
тестового окружения только по согласованной процедуре.
RPO целевой ≤24 ч для ежедневной копии; RTO — измерить, не выдумывать.
Ошибка или отсутствие подтверждения восстановления — не зелёный backup.

## 7. P.OPS

Наблюдать раздельно: логическую ёмкость/тома переходного периода,
физический PG/индексы, файлы, очередь/lease, ошибки записи, возраст копии,
последнее успешное восстановление, свежесть самого наблюдения.
80% — предупреждение, 95% — критический сигнал; ошибка записи — отдельный сигнал.
Не заполнять отчёт Dev-данными вместо production.
Инцидент и дедупликация живут вне потенциально переполненного монолита;
повторные revision не создают новый одинаковый email.
08:00 America/Denver — краткий итог с фактическим покрытием.
Неизвестное/нет доступа — «не проверено». Внешнего сторожа сейчас не включать.
Наблюдение на том же сервере не гарантирует уведомление при его полной остановке.

## Месячная цена — оценка по официальным ставкам, 28.10.2026

Отдельный аккаунт/платформа не нужны. Сервер Reserved VM уже существует,
его выбранную мощность владелец оплачивает отдельно; нового сервера не создаём.
Счёт аккаунта, включённые credits, налоги и фактическую загрузку не проверяли.

| Компонент | Опубликованная ставка |
|---|---:|
| Dev database | Включена; по документации 20 GiB, Pro/Enterprise 50 GiB |
| Production DB compute | $0,16 за compute-hour |
| Логический объём DB | $0,35/GiB·месяц |
| PITR | $0,20/GiB·месяц хранения |
| Scheduled backups | $0,09/GiB·месяц хранения |
| App Storage | $0,015/GiB·месяц |
| Передача App Storage | $0,05/GiB |
| Basic operations | $0,0004/1000 |
| Advanced operations | $0,005/1000 |

В официальной странице Data recovery сейчас указана скидка 100% на database
storage. Для долгосрочного бюджета ниже использованы ставки **без скидки**:
она может измениться, неизвестно как именно применяется в текущем аккаунте.
Скидку на compute не предполагать.

Compute-hour — единица тарификации, **не измеренный час работы нашего приложения**.
Условие из документации: запросы держат БД активной и ещё 5 минут после последнего;
частый watcher может мешать засыпанию. Для сценария 720 тарифицируемых часов
за 30 дней compute = $115,20. Это **весь расчётный compute БД**, а не автоматически
новые расходы из-за переноса: часть/всё уже может расходоваться нынешней системой.
Фактические compute-hours и прирост надо смотреть в Usage; не обещаем $1 за всю БД.

Пример начального объёма (не реальные метрики production): DB 1 GiB, 7 GiB
хранимых ежедневных копий, PITR 1 GiB, файлы 10 GiB, трафик 10 GiB,
по 1000 basic/advanced операций:

- хранение/передача = 0,35 + 0,63 + 0,20 + 0,15 + 0,50 + 0,0004 + 0,005
  = **$1,8354/мес** без storage-скидки;
- вместе с условными 720 DB compute-hours: **$117,04/мес**;
- плюс текущий Reserved VM, embeddings/AI, превышения и налоги.

Пример роста: DB 10 GiB, копии 70 GiB, PITR 10 GiB, файлы 100 GiB,
трафик 100 GiB, по 100 000 операций: хранение/передача **$18,84**,
с теми же 720 compute-hours **$134,04/мес**, плюс те же исключения.
7 GiB/70 GiB копий — расчётное допущение, реальный биллинг зависит от
сжатия, PITR-дельт и хранения. Окно 7 дней здесь пример, не согласование retention.

Dev фактически: размер базы по read-only запросу 419 221 987 байт (~0,390 GiB).
Это не объём production, не лимит диска и не месячный счёт.
Стоимость embeddings оценить после модели/токенов; сейчас $0 новых вызовов.
До этапа 1 не закупаем мощности и ничего платного не включаем.
