## 2. Настоящий источник, а не B2

`SOURCE_PROOF.json` получен повторным чтением настоящего принятого shadow B
в одной repeatable-read транзакции. Типизированные строки B конвертированы
в v3 в **нефиксируемом** техническом workspace, затем выполнен ROLLBACK.
Полный v3 root прочитан независимо и совпал с semantic SHA исходника.

В пакете:
- ревизия и полный semantic SHA — `MANIFEST.json`;
- 84 документа: **34 original + 50 new-country**, ID, SHA точного текста,
  semantic SHA документа, объём UTF-8 — `SOURCE_PROOF.json`;
- 242 архива: каждый ключ и проверенный semantic SHA там же;
- `transfer.ndjson.gz` — настоящий пакет, не макет;
- SHA DDL, манифеста, последовательности записей, сырого NDJSON и gzip,
  число записей, объёмы и максимальная строка — `FILE_READBACK.json`,
  `REVIEWED_PACKAGE.json`, `MANIFEST.json`.

Самая большая строка — примерно **66,2 МБ**, сырой поток — **1,35 ГБ**.
Поэтому прежних ограничений 20 МБ/1 ГБ недостаточно. Новый линейный
сегментный parser ограничен точными проверенными размерами пакета и жёстким
потолком 128 МиБ на строку / 4 ГиБ на поток. Gzip этих пределов не отменяет.
Пакет ещё раз прочитан этим же parser независимо от SQL, с SHA каждой записи.

Все большие файлы находятся в исключённом `generated-artifacts/`,
не в Git и не в deploy-бандле. Перед импортом снова проверить исходную
ревизию/SHA: если источник изменился, старый манифест нельзя молча заменить.

## 3. Одна кнопка, без файла с телефона

Будущая защищённая страница:
**https://talkhint.app/admin/company-import**

После публикации проверенного кода владелец входит обычным способом,
видит ревизию и параметры именно закреплённого пакета, нажимает
«Перенести» и подтверждает. До отдельного разрешения кнопка заблокирована.
Просмотр страницы не выдаёт grant и не обращается к reader книги.

Браузер не загружает файл и не передаёт owner, environment, bucket, URL,
путь или NDJSON. POST содержит только подтверждение и SHA манифеста.
Есть owner browser session, admin-права, same-origin и session CSRF.
Старых публичных `/grant`, `/consume`, `/activate` маршрутов нет.

Сервер берёт gzip из приватного App Storage проекта по закреплённому
content-addressed имени. Проверяет манифест, размер, SHA всего распакованного
потока и semantic digest записей; изменение файла приводит к отказу/откату.
Пакет или grant никогда не выдаются публичной ссылкой.

**Хранилище:** фактический результат подготовки — `STORAGE_READINESS.json`.
Если bucket ещё не создан: Tools → App Storage → Create new bucket →
имя `talkhint` → Create bucket. Это только создание ресурса, не перенос.
Загрузку и контрольное чтение выполняет технический исполнитель, не владелец
с телефона. До подтверждённой загрузки не считать путь доставки готовым.

## 4. Отдельный процесс и восстановление статуса

Тяжёлую проверку выполняет отдельный `company-import-worker.js`,
не event loop сервера Hint. Он компилируется при build, но не запускается.
Запуск — только после подтверждения владельца, с короткоживущим grant
по приватному stdin, не в аргументах, логах или окружении.

Heap дочернего процесса ограничен 2 ГиБ; до выдачи grant проверяется
фактический лимит памяти и резерв для работающего приложения:
общий лимит не ниже 4 ГиБ, свободный резерв не ниже 2,75 ГиБ.
Недостаток памяти блокирует действие, не запускает импорт «на удачу».
Реальная достаточность конкретного production VM требует проверки перед
разрешением; полноценный импорт там пока запрещён и не испытывался.

HTTP отвечает `202`; страница читает статус. Обрыв ответа — не разрешение
повторить. Состояние сверяется с сохранённым grant и shadow workspace.
При перезапуске/ошибке без подтверждения — «неопределённо», без автоматического
возобновления или повторной отправки. Повторный импорт в непустую цель запрещён.

## 5. Seed-модель и legacy

Новый барьер production привязан к подтверждённому аккаунту, независимо
от разрешения импорта. Пока normalized-источник отдельно не включён,
legacy ensure возвращает `423`, а не создаёт seed. Защищены и чтение,
и legacy-запись; остальные аккаунты и Dev не затронуты.

**Сейчас production ещё использует предыдущий код. До Publish №2 открывать
книгу там по-прежнему не нужно.** Read-only проверка пустоты владельца —
`PRODUCTION_OWNER_EMPTY.txt`; это не попытка открыть книгу.

Импорт оставляет generation=`shadow`, activated=`false`. Старый JSON и
история помещаются под техническим ключом `company-archive:<workspace>`,
не под живым ключом владельца. FK не включает legacy-reader.
Отдельного HTTP-включения источника нет.

## 6. Writer: что действительно сравнивали

Замеры B2 0,28–0,33 с для документа и около 4,07 с для роли были на ранних
ревизиях последовательного прогона. Предыдущий после-Publish стенд:
- начинал с B2 после 20 правок;
- при проверке документа добавлял произвольный текст к JSON, превращая
  документ журнала в невалидный JSON — это **не та же операция**, что в B2;
- сравнивал разные головы и последовательные правки, не повтор одного входа.

Поэтому отношение 1,7/0,3 и 7,5/4 само по себе не доказывает регрессию writer.
Недостающие старые CPU/SQL-тайминги задним числом не выдумываем.

Контрольный повтор — `WRITER_FIXED_PROBE.json`: один сохранённый физический
снимок, одна зафиксированная голова для каждого повтора, валидный JSON,
старый вариант с невалидным JSON и правка одной роли. Каждый опыт откатывается
savepoint, сама копия/обе B2 не изменяются. Время writer, выдачи ответа,
CPU, SQL по группам и полное независимое сравнение ответа сохранены.
Итоговая таблица — `WRITER_COMPARISON.md`.

Если проверка не прошла, её фактический статус отражается в пакете,
не заменяется прежним PASS. Это барьер **включения**, не самоприёмка.
Холодный кэш по-прежнему требует полного чтения **до** записи; после commit
полного чтения в `updateMany` нет. HTTP-сериализация в этих замерах не измерялась.
