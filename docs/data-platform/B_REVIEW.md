# B: этапы 1+2 в Dev — протокол проверки

## Границы

Схема A принята владельцем с дополнениями. `checkpoint-A.sql` теперь содержит
согласованную схему v2: 40 таблиц. Не перезаписывать выданный ZIP A/v1:
это исторический результат, не актуальная инструкция импорта.

Новые данные пишутся только в `company_*` Dev. До отдельной приёмки
`storage_generation=shadow`: существующий reader выбирает legacy.
Source JSON и его архив не изменяются и не удаляются. После будущего cutover
новые записи идут только в normalized; возврат к устаревшему JSON запрещён.
Никакого production grant, сопоставления аккаунтов или Publish в B нет.

## Дополнения владельца

- `company_employee_profiles`: имя, три черты, девиз, описание портрета,
  ссылка на файл, единый стиль, цвет, статус выбора, источник/версия.
- `company_employee_name_options`: упорядоченные варианты имён.
- `company_role_prompt_versions`: буквальный текст структурированного
  `prompt` из исходного документа, его hash, дата и статус
  proposed/accepted/enabled, кто и когда принял. Это НЕ обещание развёрнутого
  runtime-промпта: ссылки на общий backstory/уроки сохраняются как ссылки.
- `company_roles.mode`: hint/secretary/translator/copilot/company.
  NULL — нет подтверждённого назначения, не автоматически company.
- Два текущих паспорта P.LAB/P.LG.QA импортируются из соответствующих
  документов. Их имена выбраны, остальные визуальные предложения не выданы
  за принятую владельцем внешность. Дата отдельной приёмки имени неизвестна.
  Промпты обоих остаются **proposed**, исполнения это не включает.
- Иерархию режимных продуктовых не создаём: схема поддерживает будущую
  структуру, решение о её включении остаётся отложенным.

## Что считается доказательством

1. `IMPORT_VERIFICATION.json` существует только после COMMIT:
   actual counts, source/reconstructed semantic SHA-256, hashes архива,
   source revision, schema digest и статус shadow.
2. `INTEGRATION_TESTS.json`: реально выполненные проверки PostgreSQL
   на изолированных синтетических владельцах с удалением именно этих fixtures.
   Сюда не копируются пользователи, звонки, ключи или задания лаборатории.
3. Реальная B-сверка читает все архивные payload порционно и сверяет с A.
   Наличие строки/ID не заменяет проверку содержимого.
4. Все таблицы сверяются построчно. Числа PostgreSQL приводятся к исходному
   числовому типу; `present_fields` сравнивается как набор имён полей, не
   случайный порядок ключей JS-объекта. Порядок массивов не меняется.
5. Кодеку проверяется null ≠ отсутствие, [] ≠ {}, UTF-8 digest,
   UTF-16 длина iPhone/JS, JSON pointers и защита от prototype pollution.
6. Writer проверяется через прежние domain-команды: CAS, многокомандный
   rollback, сохранность старой версии и неизменность legacy после записи.
7. Теневая схема не подключает новую роль, tools, память CrewAI,
   голосовую запись, модель или новый способ почты.

## Обратимое размещение явных данных

`company_record_locations` содержит только указатели/имена колонок/ключи.
Здесь нет JSON-модели. Это техническая привязка неизменного JSON-контракта
к строкам нормализованных таблиц. Чтение использует allowlist таблиц и
проверяет итоговый digest; нет SQL-идентификаторов из входного документа.

`company_extra_fields` хранит остаточные типизированные значения и описания
контейнеров, не JSON-монолит. Отчёт разделяет **скалярные значения**,
**контейнеры формы** и **байты строк**: общее число строк не равно числу
невыделенных бизнес-полей.

### Кандидаты на следующие явные таблицы

Решение после сверки фактического отчёта, не скрытая смена схемы:

1. `decisions.before/after`, `strategyChange`: неизменяемые deduplicated
   audit snapshots с digest и ссылкой. Сейчас в EAV сохраняется каждый
   исходный фрагмент. Это основной кандидат по объёму строк.
2. `strategy`, `competitorDirectory`, `analystPreparation`: сегменты,
   гипотезы/эксперименты, конкурентные карточки и подготовка аналитика.
   Сейчас типизированы обратимо; подключать исполнителей из этого нельзя.
3. Редкие расширения legacy elements (coordination) и ссылки drafts:
   отдельные связанные записи при росте употребления.
4. Описания пустых/вложенных контейнеров operatingModel: это не факты
   сотрудников. Их много из-за 41 сохранённой версии; можно заменить
   декодированием по фиксированному versioned contract, но только после
   той же побайтовой/семантической сверки.

Профили, основные поля ролей, действий, документов, связей, решений и
промптов не предлагается оставлять только в EAV.

## Работа Hint

Сменяется только источник чтения документа, когда для подтверждённого
owner/environment явно включено normalized. До этого — прежний источник.
P.LAB-оценка, промпты, QA, watchdog, частота, очередь, outbox и доставка не
меняются. Активный normalized-документ недоступен/повреждён — честная ошибка,
не чтение старого JSON. `get_document` имеет прямой reader одного документа,
не разворачивает всю историю ради письма/книги.

## Production №1 — не выполнено

Publish переносит только схему. Содержимое — отдельная owner-authenticated
операция после подтверждения привязки аккаунтов. Продуктовые ID не меняются;
локальный `owner_key` заменяется только по этой привязке.

Production пустоту надо повторно проверить непосредственно перед импортом.
Если появилась модель — остановиться, не перезаписывать. Переносится только
структура компании и её архив; calls/users/call_lab_*/sessions/секреты не
входят в комплект. Нельзя использовать «overwrite production data».

Перед cutover production нужны те же hashes/ID, отрицательные auth/env тесты
и проверка прямого чтения журнала лабораторией из production. Результат
Dev не считается этой проверкой. Не предполагать, что приватный transport
или owner grant уже проверен: сначала обеспечить и проверить авторизованный
способ передачи, не открывать импорт анонимно.

## Ограничения приёмки

Это инженерные проверки, не независимый ручной проход Claude/владельца.
Signed-in экран книги проверяется отдельно; тест репозитория не является
скриншотом экрана. Ежедневные backup/restore и общий P.OPS — этап D, не
выдавать сохранность версии в B за выполненную ежедневную резервную копию.
Файлы/pgvector — этап C, не создавать под них новые аккаунты.
