# Контрольная точка A — окончательная схема для сверки

Версия схемы: **1**. Источник Dev: **new-country / root rev912**.
Статус: **подготовлено, не применено**. DDL: `checkpoint-A.sql`.
Порядок владельца: A → B (1+2, Publish №1) → C (3+4, Publish №2) →
D (5–7, Publish №3) → E (итоговый акт). На каждой границе нужно новое «да».
Публикует владелец. Нельзя считать приёмку A разрешением production-переключения.

## 1. Что проверено фактически

Read-only транзакция Dev; все исходные данные и архив прочитаны без записи.
В `SOURCE_MANIFEST.json` — время, source revision, SHA-256 и количества.
Полная инвентаризация включает обе гипотезы и сохранённые архивные payload:

| Объект | original | new-country |
|---|---:|---:|
| Legacy elements | 151 | 30 |
| Legacy relations | 285 | 23 |
| Документы | 34 | 50 |
| Предложения | 71 | 0 |
| Решения | 602 | 312 |
| Черновики задач | 5 | 0 |
| Версии operating model | 0 | 41 |
| Текущие узлы | 0 | 866 |
| Текущие связи | 0 | 4042 |

В текущем графе: 43 роли, 335 действий, 58 ресурсов, остальные типы —
в manifest. Это не 866 сотрудников. Сохранённых архивных записей: 242
(71 снимок корня, 171 content-addressed chunk).

Инвентарь: 1423 наблюдаемых пути структуры, 5939 путей внутри JSON-документов,
1967 путей архивных payload. Это пути с wildcard для элементов массивов,
а не число значений/строк будущей базы. Наблюдаемые типы не заменяют контракт
опциональных полей из TypeScript/Zod; их исходники включены в пакет.

Читались сохранённые документы: паспорт продукта, глава Hint **v4**,
P.LAB **v3**, P.OPS **v3**, журнал улучшений **v28 / 13 случаев**.
Версия без числового поля `version` не выдумывается: используется hash текста.
Нет новых выводов лаборатории или изменения её промптов.

Текущие ID, endpoints связей, входы действий, документы шаблонов и связи
документов проверены. Ошибок этих ссылок не обнаружено.
`referenceIds` — не только узлы: в них также документы, legacy elements,
конкуренты, strategy entries и analyst-preparation. Этот набор проверяется
тем же классификатором, что действующий домен; нельзя навесить FK всех
referenceIds на таблицу узлов и потерять внешние разделы.

**Production, read-only факт:** `talkhint_project_models` содержит **0 строк**,
`new-country` отсутствует. Это не потеря production-звонков и не утверждение,
что лаборатория не работает: её таблицы отдельные.
Поэтому механизм начального переноса описан ниже как утверждённая передача
структуры из Dev, а не backfill несуществующей production-модели.
Проверка состава и готовности Hint к звонку в рамках A не выполнялась.

## 2. Как читать DDL

### Основная схема

- `company_workspaces`, `company_hypotheses`, `company_model_revisions`:
  владелец, физическое окружение, источник, CAS revision и поколение хранения.
- `company_operating_revisions`, `company_entities`:
  прежние ID и все 41 версии графа. Явные скалярные колонки, не JSONB-монолит.
- `company_roles`, `company_actions`, `company_resources`: подтипы того же узла,
  не новые паспорта и не параллельный каталог.
- `company_node_refs/inputs/schedules/metrics/reporting/register`,
  `company_node_material_refs`: связи, порядок массивов, KPI, формы и ресурсы.
- `company_links`, `company_customer_stages`, `company_stage_reports`:
  прежние ID, направления, готовность, пути B2C/B2B и результаты этапов.
- `company_legacy_elements/details/relations`: прежний отдельный namespace.
  Совпадение строк ID в двух namespaces не означает слияния сущностей.
- `company_documents/versions/links`: прежний ID, полный исходный текст,
  SHA-256 UTF-8, длина UTF-16, ссылки и версии.
- `company_decisions/refs`, `company_proposals`, `company_task_drafts`:
  решения, источники, состояние приёмки и исходные ссылки.
- `company_journal_cases/events/issue_attempts`, `company_report_records`:
  существующие случаи, история именно проблемы, попытки/эффект, отчётность.
- `company_source_archives`, `company_import_runs/checks`: неизменяемый
  источник и проверяемый протокол переноса.

### Остальные поля — не теряются

`company_extra_fields` хранит **типизированные отдельные значения** по точному
JSON Pointer, scope и revision: string/numeric/boolean/null/object/array.
Контейнеры и их размеры, позиции массивов, отсутствующее поле и null различаются.
Это необходимо для strategy, competitorDirectory, analystPreparation,
coordination, неодинаковых audit before/after, расширений и старых форм.
Основной граф и документы в эту таблицу вместо нормализации не складываются.
В `FIELD_INVENTORY.json` у каждого пути указано семейство назначения.

При B нужен исполняемый mapping manifest для каждого импортированного значения:
source pointer → таблица/ключ/колонка → обратно в исходный контракт.
Генератор реконструкции обязан отклонить неизвестный/пропущенный путь;
нельзя считать надпись `unmappedPaths: 0` доказательством выполненного импорта.
Сейчас она означает лишь, что для каждого пути назначена схема хранения.

`present_fields` сохраняет опциональность известных полей, ordinal —
порядок массивов. Даты источника сохраняются **как исходный text**:
пустая дата/дата без часового пояса не превращается в выдуманный UTC.
Служебные timestamps новой системы — `timestamptz`.
`source_revision` версии графа означает revision снимка, из которого она
импортирована; неизвестную исходную root revision её создания не сочинять.

### Документ и его нормализованное содержимое

Старый текст каждой версии сохраняется побайтно в `document_versions`.
Для обычного документа это канонический текст. Для журнала/типизированной
формы после переключения канонические текущие данные — нормализованные строки;
сохранённый текст версии — их неизменяемый опубликованный результат.
Запись содержимого и новой версии представления — **одна транзакция**,
не два независимых источника и не два раздельных dual-write процесса.
Исторические тексты не пересобираются сегодняшним форматтером.
Нестандартные поля событий/попыток сохраняются в typed fields, а не выбрасываются.
Пустой или отсутствующий owner effect остаётся неизвестным, не «помогло».

### Сохранение истории

Нормализуются текущие обе гипотезы, их содержащиеся истории и версии графа.
Все 242 старых archive payload остаются неизменяемыми и доступны через прежний
owner-scoped исторический reader. Старая root revision может читаться из архива,
её не нужно переизобретать из неполного набора новых событий.
Все новые изменения после cutover имеют версии в новой схеме.
Хеши всех старых payload перечислены в `HISTORY_HASHES.json`.
Исходный JSON не удаляется, не перезаписывается новым «похожим» JSON.

### Ограничения DDL

DDL — конкретный контракт v1 для этапов 1+2, **но ещё не применён**.
Статическая проверка не равна проверке PostgreSQL: исполнение схемы и
constraint/rollback/concurrency-тесты — часть B после разрешения владельца.
Подтип role/action/resource должен совпасть с kind базового узла: проверяет
import/domain validator и обязательные отрицательные тесты B.
Полиморфные material refs проверяет домен; SQL не может обеспечить обычным
FK выбор одной из нескольких целевых таблиц.
Для решений прошлые ссылки могут указывать на удалённое историческое состояние;
их сохраняем и проверяем в соответствующей версии, не только в текущем графе.
RLS не заявлена установленной. Ни агент, ни браузер не получает SQL credentials;
owner/env/scope проверяется серверным репозиторием до доступа к строкам.
Composite FK не заменяет эту проверку доступа.

## 3. Импорт и сверка в Dev — только после «да» на A

1. Зафиксировать согласованный SQL digest; описать таблицы в `shared/schema.ts`.
   Применить DDL только Dev. Ни DDL в startup/build, ни custom prod-migrate.
2. Выбрать единственный канонический workspace явно, привязать владельца.
   Зафиксировать неизменяемый root snapshot + chunks и их manifest.
3. Создать import run с source revision, схемой, hash. Импортировать
   идемпотентными порциями в **неактивное** поколение; Hint не читает его.
   Совпадение ключа с иным digest — ошибка, не `ON CONFLICT DO UPDATE`.
4. Сначала scope/revisions, затем сущности и документы, затем ссылки.
   Не угадывать новые ID, не чистить «лишние» исходные строки.
5. В каждой порции — короткая транзакция; контрольные точки позволяют
   продолжить тот же run после падения без повторного письма/разбора.
6. Сверить каждую текущую сущность, каждую версию и документ. Проверить
   одинаковые наборы ID и отсутствие добавленных/потерянных строк.
   Сверять **семантический hash JSON с сортировкой object keys**, а для текста
   документа — SHA-256 исходного UTF-8 без сортировки/нормализации/trim.
7. Проверить reconstruct → полный старый JSON и readRevision.
   Пропущенное поле, порядок массивов, null/отсутствие, unicode, timestamps,
   legacy original и все 41 версии проверяются отдельно.
8. Теневой репозиторий не меняет production и не становится источником.
   Сравнить книгу, get_document, get_product_chapter, get_team/get_roadmap,
   get_work, search_materials, JSON-export и downloads в старых формах.
   Допустимы лишь заранее объявленные новые диагностические поля, не потеря старых.
9. Если пока импортировалось источник изменился — pin новой revision/дельта,
   повторная сверка. Cutover запрещён по старой ревизии.
10. До переключения — восстановление пробного нормализованного снимка в
    изолированном Dev test scope и его сверка; это разовая безопасность B,
    не заявление, что ежедневное расписание резервных копий D уже включено.
11. Атомарный CAS меняет storage_generation только при полном PASSED manifest.
    После него старый JSON — read-only архив. Мутации идут только в новый
    репозиторий. Отдельный advisory lock/row lock модели — краткий,
    не блокировка таблиц calls/call_lab_* и не остановка Hint.

## 4. Production после Publish №1 — согласуем этот механизм в A

**Факт: production-модели нет.** Поэтому предлагаем перенос утверждённой
**структуры Dev**, включая обе гипотезы и её архив. Не всю Dev-базу.

Предлагаемый механизм (реализация/проверка — B):

1. В Dev собрать streamable versioned bundle: schema version, source revision,
   модель, неизменяемые chunks, digests, ID/count manifest. Зашифрованный
   транспорт HTTPS, gzip с ограничениями распаковки/объёма. Не Git и не build asset.
2. Обычный Publish переносит только согласованную **схему** Replit.
   В Publish не включать «overwrite production data».
3. В существующем приватном admin-контуре — owner-authenticated approval/import
   операция, без публичного MCP и без универсального SQL/API.
   Она принимает **только** согласованный bundle с точным digest/областью.
   Передача — возобновляемая загрузка частей. Владелец подтверждает привязку
   Dev model owner к своему production аккаунту; совпадение строк user ID
   между базами нельзя предполагать.
4. После owner grant роль HEAD.07 передаёт пакет технически по узкой
   краткоживущей upload capability, привязанной к пользователю, manifest,
   окружению, разрешённым типам записей и лимиту размера. Это не новый
   постоянный API key и не выгрузка секретов. Grant создаётся через вход
   владельца; не подделывать сессию и не обходить авторизацию.
   Если рабочий способ передачи capability в среду исполнителя не проверен,
   это BLOCKED, а не повод открыть endpoint анонимно. Запасной путь —
   загрузка того же пакета владельцем через приватный admin import.
5. Проверить, что production target всё ещё пуст. Если появилась модель —
   **стоп**: нельзя перезаписать её снимком Dev; нужна отдельная сверка/решение.
6. Добавить только owner-bound строки модели/архива и новые company_* строки
   в неактивное поколение. `owner_key` адаптируется по подтверждённой привязке;
   бизнес-ID/тексты/порядок/версии/история не меняются.
7. Повторить в production counts/ID/digest, старое и теневое чтение, restore
   safety check и тесты авторизации. Только затем атомарный cutover.
8. Hint jobs, controls, outbox, текущие звонки, пользователи, sessions,
   номера, секреты, тексты звонков и настройки **не копируются и не меняются**.
   Не перезапускать конвейер лаборатории ради импорта и не трогать его выключатель.
   Ранее запущенный разбор/отправка продолжает работать; отдельные таблицы
   и ограниченная нагрузка import worker не должны удерживать их блокировки.

Это **не production DDL-скрипт** и не запуск миграции на старте: schema —
Publish; содержимое — отдельная узкая авторизованная операция после согласования B.
Передача/включение не выполняются сейчас. Bundle не должен раскрывать личные
данные из модельных документов; тот же приватный доступ и проверка назначения.

### Откат

До cutover — выключить shadow-reader; старый источник работает как прежде.
После новых нормализованных записей старый JSON уже отстаёт: переключать на него
как на актуальный источник нельзя. Нужен совместимый reader либо сверенный
обратный экспорт **всех новых изменений** с отдельным разрешением.
Ничего не удалять. Проверенный пакет/архив остаются доступны.

## 5. Пакет B и следующие контрольные точки

B, один ZIP: actual DDL diff, schema version/digest, manifest обеих сторон,
counts и ID diffs **0**, документы и history hashes, shadow comparisons,
отрицательные owner/env тесты, idempotency/crash/concurrency/restore tests,
репозиторий записи и HTTP/MCP/download tests, production transfer runbook,
перечень непроверенного. Условие «готово» — не количество таблиц, а равенство
чтения плюс проверенная запись без потери истории. Затем «да», Publish №1
владельцем, отдельно перенос и production checks.

C, один ZIP: файлы в private App Storage, реальная проверка digest/доступа,
память pgvector с источниками/устареванием/изоляцией; затем «да», Publish №2.
До разрешения моделей/embedding расходов не вызывать новые модели.

D, один ZIP: сквозная изоляция, backup coverage БД **и объектов**, ежедневная
копия, реальное изолированное восстановление, P.OPS 80/95%, запись/свежесть/
сбой проверки; затем «да», Publish №3. Внешнего сторожа не подключать молча.

E: единый акт выполненного: что/откуда/куда, source/target revisions,
все manifest и тесты, принятые исключения, реальные шаги восстановления,
где смотреть инциденты и что именно P.OPS контролирует.
Непроверенное не отмечать зелёным.

## 6. Границы текущей работы

Промпты P.LAB/P.LG.QA, экран «Команда» и новые роли — пауза до окончания
переезда. Их незавершённость не повод менять работающий Hint.
Расходы **не пересчитываем** и Usage не запрашиваем — уточнение владельца.
Новые аккаунты/провайдеры, остановка лаборатории, письма, вызовы моделей,
перенос данных, создание таблиц проекта и публикация в A не выполняются.
Пакет A — схема и доказательства инвентаризации; не акт состоявшегося переноса.
