# Publish №1 — проверка перед разрешением владельца

Статус: пакет для независимой сверки; не разрешение публиковать.
Основание: приёмка владельцем B2 v2 и приложенный проход Claude.
Изменений поведения приложения, DDL в production, импорта и активации нет.

## 1. Что действительно предлагает Publish

Получен фактический `explainSchemaDiff`, а не только сравнение файлов схемы:
**196 операторов: 85 CREATE TABLE, 106 ADD CONSTRAINT, 5 CREATE INDEX.**
Удалений/очисток, изменений существующих столбцов и предупреждений о
несовместимости этот снимок diff не содержит. Это предварительный снимок;
перед нажатием Publish его нужно сопоставить с актуальным диалогом публикации.

Полный список — `TABLES.csv` и `TABLES.md`, полный diff — `PUBLISH_DIFF.sql`,
исходный ответ проверки — `SCHEMA_DIFF.json`. SQL приложен ТОЛЬКО для чтения.
Не запускать его вручную, из build или при старте.

| Группа | Количество | Состояние после обычного Publish, до отдельного импорта |
|---|---:|---|
| Схема A/B, v2, `company_*` без `company_v3_*` | 40 | Пустой неиспользуемый архив совместимости B |
| Бизнес-таблицы v3 | 34 | Пустая структура целевого хранилища |
| Служебные таблицы v3 | 11 | Пустые контракты, индексы версий/документов, снимки, разрешения импорта и реестр |

Выбран разрешённый владельцем вариант: **сохраняем структуры B**, но явно
маркируем их в этом пакете как пустой неиспользуемый архив совместимости.
Это документальная маркировка, не обещание SQL COMMENT в production.
Все 40 имён перечислены с этим статусом; данные B туда не импортируются.
Не удаляем таблицы Dev ради исключения из diff. Текущий генератор Dev v3
использует структуры B как шаблоны колонок (`LIKE`); менять этот контракт
в принятом B2 сейчас не требуется.

В v3 нет таблиц `company_v3_extra_fields`/`company_v3_record_locations`:
остаточная структура хранится контрактами и кадрами. Названия всех 45 таблиц
v3 находятся в списке; профиль сотрудника и версии промпта в нём явные.

Publish переносит схему, не строки Dev. **Не включать опцию перезаписи/
копирования данных Dev в production.** Иначе это другой, не согласованный
сценарий. Обе B2-копии с тестовыми правками остаются только в Dev.
После Publish отдельно проверяем фактическую пустоту всех новых таблиц.

## 2. Почему импорт и переключение не произойдут сами

- `.replit`: обычный build и запуск приложения; команды миграции компании
  или переноса данных не добавлялись.
- `script/build.ts`: сборка приложения/проверка наличия зависимостей лаборатории;
  не вызывает `ddlV3`, импорт или активацию.
- `ddlV3()` возвращает текст схемы. Из запуска сервера он не исполняется.
- `OwnerImportService` — подготовленный внутренний сервис без подключённого
  HTTP-маршрута и без регистрации при старте. Production запрещён по умолчанию.
- Активный источник выбирается по записи owner/environment с
  `generation='normalized'` (или прежнему v2-флагу). Создание пустых таблиц
  такой записи не создаёт. Текущий источник остаётся прежним.
- Не менялись настройки лаборатории, дежурного, почты, звонков и iOS.
  Это не новая проверка их production-готовности.

Важно: существующий запуск приложения в целом выполняет прежние фоновые
функции (включая лабораторию/дежурного). Подтверждение выше относится именно
к **импорту компании и переключению источника**, не к обещанию «сервер вообще
ничего не записывает». Контур Hint не выключается для миграции.

## 3. Подтверждение аккаунта Dev → production

Read-only проверка пользователей и метаданных дала:
- исходный workspace B: revision 912, `shadow`, соответствует email владельца;
- ID аккаунта Dev и production совпали;
- у найденного production-аккаунта записи `talkhint_project_models` нет;
- все 85 новых таблиц отсутствуют в production по текущему diff.

Идентификаторы и снимок результата — `ACCOUNT_BINDING_PROPOSAL.json`.
Ни один grant или факт привязки в базу не записан. Совпадение ID/email —
основание предложения, **не замена явного согласия владельца**.

**Запрос владельцу, после независимой сверки этого пакета:**
1. Проверить предложенную пару в JSON: это существующий аккаунт, не регистрация.
2. Отдельно подтвердить в чате: «Привязку Dev → production из пакета
   подтверждаю только для модели new-country. Импорт пока не разрешаю».
3. После разрешённого Publish войти в существующий аккаунт на
   https://talkhint.app. Токены, cookies и ключи в чат не присылать.
4. Перед реальным переносом сервер повторно проверяет owner по авторизованной
   сессии, права, CSRF, подтверждённую пару, свежую ревизию и SHA пакета,
   пустоту цели. Если цель занята — стоп; никакого удаления/перезаписи.

Сейчас отдельной кнопки привязки/импорта нет. B2 содержит сервис, а не готовый
пользовательский маршрут. Подключение защищённого обработчика и его тесты —
обязательная часть подготовки реального импорта, до отдельного «да» на него.
Нельзя обещать, что после одного Publish такой интерфейс уже появится.
Для источника берём настоящую утверждённую модель, **не B2-копии после 20
искусственных правок**. Привязка не переносит пользователей, звонки, номера,
почту, платежи и чужие данные; она определяет получателя модели компании.

## 4. Не путать три разрешения

1. Сверка этого пакета → отдельное разрешение владельца на Publish №1.
2. Подтверждение пары аккаунтов → не разрешение на импорт.
3. Отдельное «да» на импорт/включение после готовности и проверок.

До включения новой базы основным источником обязательно устранить полное
чтение модели из ответа `updateMany` после записи, сохранив согласованный
контракт клиентов и проверки данных. Это **не сделано** данным пакетом.
Около 4 секунд на изменение ролей — наблюдать на следующих проверках;
20 правок не доказывают поведение после тысяч ревизий.

Обе тестовые копии B2 и таблицы B сохраняются. Удаление — только отдельное
решение владельца и точный список. Самоприёмки нет.

## 5. Что проверено и как

- Фактический read-only diff Dev → production: 85 новых таблиц; только
  создание таблиц, добавление ограничений и индексов на них.
- Read-only сверка аккаунтов и отсутствия legacy-модели у выбранной цели.
- Просмотр build/startup, маршрутов компании, селектора источника,
  генератора DDL и подготовленного импорт-сервиса.
- Скрипт упаковки проверяет классификацию всех SQL, группировку таблиц,
  отсутствие destructive-флагов и проверяет SHA каждого файла ZIP.
- Исполняемый код не менялся: предыдущие 440 успешных тестов B2 и его
  нагрузочный прогон не выдаются за новые тесты или production-приёмку.
- Таблицы production после Publish, сам импорт и signed-in интерфейс
  книги этим пакетом не проверены: публикации не было.
