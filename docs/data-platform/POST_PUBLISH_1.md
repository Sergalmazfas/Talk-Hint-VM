## 2. Ответ о старой модели и порядке включения

Есть две разные схемы:

1. B: `company_workspaces.owner_key` связан с
   `talkhint_project_models.owner_key`.
2. v3: у `company_v3_workspaces.owner_key` такого FK нет.
   Для старых архивов v3 остаётся цепочка
   `company_v3_archive_refs` → `talkhint_project_model_history` →
   `talkhint_project_models`.

Прежний внутренний importer переносил родительский JSON под **живой owner_key**.
Даже при `generation=shadow` старый `PgModelRepository` мог бы прочитать этот
JSON. Значит, «shadow» само по себе недостаточно, чтобы исключить скрытое
изменение книги до отдельного разрешения.

Исправление: legacy-родитель и история хранятся под отдельным техническим ключом
`company-archive:<workspace>`. Архивные ссылки указывают на него. Живой owner_key
не создаётся и не перезаписывается. Выбор источника по-прежнему требует
`generation=normalized`; импорт всегда заканчивается `shadow`.
Включение через импорт запрещено даже внутреннему вызову с `true`.
HTTP-операции включения нет.

**До отдельного «да» на включение:**
- книга и обычный `get_document` используют прежний источник;
- лабораторный direct-reader не выбирает shadow и сохраняет прежний путь;
- импортированный журнал не подставляется вместо рабочего;
- появляются только кандидат v3 и архив под техническим ключом.

Если после импорта открыть прежнюю пустую production-модель, обычный старый
reader может штатно создать исходную seed-модель живого владельца. Он не начнёт
читать импортированный архив. Перед будущим включением это нужно повторно
проверить: обнаруженная новая рабочая запись — **стоп и отдельная сверка**,
не автоматическая очистка/перезапись. Блокировка bootstrap и импорта
согласована одним owner-scoped advisory lock; чужих владельцев она не блокирует.

## 3. Подготовленный HTTP-обработчик

Код зарегистрирован в Dev:
- `GET /api/admin/company-import/status`;
- `POST /api/admin/company-import/grant`;
- `POST /api/admin/company-import/consume`.

В текущей версии `reviewedImportApproval = null`.
Обработчик закрыт (423) и не выдаёт разрешений, не создаёт сессий импорта
или кандидатов. Публикация этого кода не является согласием на импорт.

При отдельном будущем разрешении требуются:
- действующая браузерная сессия владельца и существующий admin gate;
- точное совпадение owner/environment с подтверждённой серверной привязкой;
- same-origin и отдельный CSRF-токен сессии, не токен из тела запроса;
- зафиксированный проверяющим manifest: source owner/environment/workspace,
  свежая revision, SHA-256 schema/manifest/records и semantic SHA полного JSON;
- одноразовое разрешение на 10 минут, в БД только его hash;
- внутри одной транзакции: блокировка разрешения, проверка срока/повтора,
  блокировка owner, повторная проверка пустой цели, чтение bounded NDJSON;
- allowlist таблиц/полей, пересчёт потока, проверка корня, индексов документов,
  архивов и фиксация consumed вместе с кандидатом.

Bearer/MCP авторизация сама по себе не подходит. В чат не нужны cookies,
session/CSRF-токены или одноразовый grant. Код ошибок не раскрывает SQL/данные.
NDJSON читается потоком: лимит строки 20 MiB, общего потока 1 GiB,
число строк задано manifest и ограничено сверху.
Перед реальным переносом нужно проверить максимальную строку **настоящего**
пакета. Превышение — отказ и согласованное изменение формата, не молчаливый
обход лимита.

### Последовательность до реального импорта

1. Claude сверяет этот пакет; владелец подтверждает привязку аккаунтов отдельно.
2. Непосредственно перед переносом перечитать настоящую принятую shadow B,
   revision и весь semantic SHA. Приложенный `sourceProof` — текущая проверка,
   не вечный пропуск. Нельзя экспортировать изменённые B2-копии.
3. Подготовить v3 transfer-кандидат **из shadow B**, не из тестовых копий;
   исходная B неизменна. Сверить обратное чтение, 84 документа, архивы,
   размер каждой NDJSON-строки, record count/digest, schema/manifest SHA.
   Этот production-пакет пока не создан, его контрольную сумму не выдумываем.
4. Владелец отдельно разрешает импорт точного пакета. Только после этого
   можно заполнить серверную запись согласования и выпустить обработчик.
   Уже сделанный Publish №1 нового обработчика не содержит: понадобится
   отдельная публикация подготовленного кода. Самостоятельно не публикуем.
5. Авторизованный владелец получает CSRF/grant и передаёт проверенный поток.
   Это создаст только shadow-кандидат. Импорт до этих согласований не запускать.
6. Провести проверки из §5. Затем отдельное решение о включении.
   Защищённое включение будет отдельным изменением/согласованием;
   текущий пакет не содержит скрытого автоматического cutover.

## 4. `updateMany`: полный контракт без повторного полного чтения после записи

Раньше после commit повторно декодировалась вся выбранная модель с историей.
Теперь используется ровно тот снимок, который клиент уже читал, с ключом
pool + environment + owner + hypothesis + root hash + revision.
Кэш ограничен одной выбранной моделью на pool и TTL 120 секунд; это
не второй источник истины. Writer проверяет актуальную revision под SQL lock.
Ответ собирается из подтверждённого рабочего изменения и неизменённой истории,
не клонируя/читая её заново. Контракт полного ответа сохранён.

Честная граница: при холодном кэше остаётся одно полное чтение **до записи**.
Экспорт и полное GET-чтение не ускорены этим изменением. Сериализация полного
HTTP-ответа не входит в замер repository. Это не обещание «вся страница за 1 мс».

Замеры и равенство SHA полного ответа независимому DB-reader —
`DEV_PROBE.json`. Два типа правки (документ и роль), старый/новый путь.
Тест использует отдельную **нефиксируемую** копию полноразмерной B2 только для
производительности, не как источник production. Все записи прогона откатываются
одним внешним ROLLBACK; ни одного DELETE/DDL. Обе сохранённые B2-копии и B
не изменяются. Role writer сам по себе ещё требует наблюдения;
устранение повторного чтения не означает достижения норматива 4 секунды.

## 5. Проверка ПОСЛЕ будущего импорта, до включения

В защищённом read-only проходе кандидата, не через живую книгу:

| Проверка | Требуемое доказательство |
|---|---|
| Источник | настоящий shadow B, свежая revision и owner binding |
| Передача | schema/manifest/records SHA, точное число записей |
| Вся модель | semantic SHA реконструкции = source |
| Все разделы | количества, стабильные ID, нулевые потерянные/лишние ID |
| Документы | все 84 текущих документа: прямой reader, ID, побайтовый UTF-8 SHA |
| История | полный перечень принятых архивов (в прежней сверке 242), SHA каждого |
| Изоляция | shadow не выбран, нет canonical live-owner JSON от importer |
| Журнал | чтение нужного документа в production-кандидате, текст/SHA/revision |
| После отдельного включения | active direct-reader журнала, get_document, книга, JSON-export читают тот же источник |
| Работа Hint | без новых звонков — готовность worker/очередей; контрольный звонок только владельцем позже |

84 документа — суммарно обе гипотезы, не 84 только в new-country.
Свежий sourceProof показывает 50 в new-country; исходная гипотеза содержит
34 по принятому инвентарю с тем же полным semantic SHA.
Это разграничение — `SOURCE_FRESHNESS.json`, не замена будущей прямой сверки.

84 и 242 — принятый базовый инвентарь. При свежем источнике не подгонять
изменившееся число: сначала показать diff и получить сверку.
Тесты с малым fixture не заменяют этот полноразмерный проход.

## 6. Отмена / откат

- До commit: любой отказ, обрыв или несходящийся digest → ROLLBACK всей
  транзакции кандидата и архива; одноразовый grant не помечается consumed.
  Не повторять неоднозначно завершённый HTTP-запрос вслепую: сначала
  проверить grant/candidate через отдельную авторизованную сверку.
- После commit shadow: ничего не удалять. Кандидат и его архив сохраняются,
  grant consumed, работающий источник остаётся прежним. Согласование можно
  закрыть следующим решением/выпуском, не очищая таблицы или чужие строки.
- После будущего включения: отдельный план нужен **до** разрешения cutover.
  Нельзя просто переключить на старый JSON, если уже были новые записи.
  Сначала остановить только запись модели компании, зафиксировать revision,
  проверить новые записи и согласовать возврат; Hint не останавливать.

Этот пакет не выполняет откат, очистку, import или включение.
