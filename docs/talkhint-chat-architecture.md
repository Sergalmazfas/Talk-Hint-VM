# TalkHint Chat — архитектурное предложение

Документ для согласования владельцем. Основание: четыре макета, исходное
задание на архитектуру и дополнение с приоритетом долговременной памяти.
Проверены исходники; production, реальные пользовательские данные и внешние
сервисы не опрашивались. Ниже чётко разделены найденное и предлагаемое.
Ничего не внедрено. Тарифы ChatGPT, стоимость моделей, себестоимость,
финансовая модель и биллинг не исследуются.

## 1. Главный ответ

TalkHint Chat должен быть новым пользовательским интерфейсом и управляющим
слоем над существующими карточками, планами, поручениями и результатами.
Не новым телефонным движком, вторым планировщиком звонков или копией
Секретаря. Долговременная память — это управляемые подтверждённые объекты
пользователя, а не бесконечная переписка в системном промпте.

Чат предлагает, сервер проверяет полномочия и фиксирует действие, существующий
инструмент выполняет. Модель сама не выдаёт себе разрешение на звонок,
отправку письма, публикацию или изменение подтверждённой памяти.

## 2. Карта найденных компонентов

| Область | Что найдено в исходниках | Переиспользование и ограничение |
|---|---|---|
| Пользователь и настройки | `shared/schema.ts`: users, язык, userContext; защищённые маршруты в `server/routes.ts` | Существующая идентичность пользователя. Не копировать users целиком в модель: в таблице есть служебные и секретные поля. Подтверждённый профиль не равен произвольному userContext |
| Номер и профили звонков | `server/callProfiles/routes.ts`: чтение профилей, защищённое подключение номера | Использовать существующее назначение номера. Профили personal/work не превращать в обязательный выбор профессии |
| Карточки знаний | `shared/schema.ts`: knowledge_cards; `/api/cards` в `server/routes.ts`; операции в `server/storage.ts` | Уже есть owner-scoped CRUD, title/body, personal/work. Пока не полноценная память с версиями, источниками и предложениями изменений |
| Контакты | contact_memory, `/api/contacts`, `server/storage.ts` | Сохранить ID и существующую связь пользователь + телефон. Автоматическая сводка звонков не становится подтверждённым фактом о пользователе |
| Схема плана | `shared/callPlan.ts` | Использовать общие goal, ownerFacts, sayAsk, expectedQuestions, unknowns, disclosurePolicy, language, executor, targetPhone. Не терять семантику сказать/спросить/запрет |
| План Hint | `server/callPlans/store.ts`, `server/callPlans/routes.ts` | Реальная таблица, hash, повтор по request ID, superseded/consumed, TTL 24 ч, привязка к исходящему звонку. Это не бессрочная память |
| Внешний ChatGPT | `server/chatgpt/routes.ts`, `server/chatgpt/toolMetadata.ts` | Есть подготовка обоих типов планов, чтение задач, звонков и результатов. Маршруты имеют собственные scopes и owner-проверки; внутренний чат не должен подделывать эти credentials |
| Секретарь | `server/secretary/routes.ts`, secretary_tasks и calls в `shared/schema.ts` | Переиспользовать защищённую подготовку/подтверждение, request ID, выполнение и отчёт. Не создавать вторую очередь исходящих звонков |
| Старый чат | `/api/chat` в `server/routes.ts` | Найден PREP/LIVE обработчик: в конкретном запросе передаёт system и одно user-сообщение. Это не доказательство наличия постоянных диалогов, прав и контекста нового чата |
| PREP | `server/prepare.ts` | Есть диалог подготовки, голосовая транскрипция, сериализация по пользователю и защита reset. История в Map; не использовать как источник постоянной переписки после перезапуска |
| iOS | `ios/TalkHint/UI/PrepareViewController.swift`, карточки и контакты в существующем клиенте | Сохранить работающую подготовку и доменные API. Чат проектируется внутри существующего TalkHint, без миграции клиента и возврата Copilot |
| Календарь | `server/incomingSecretary/ownerCalendarRoutes.ts` | Уже есть отдельный пользовательский OAuth для рабочего номера, статус, выбор календаря, отключение. Не путать с Dev-коннектором из calendarRoutes. Наличие этих маршрутов не доказывает готовность общей записи событий из чата |
| Файлы, поиск, Gmail, геолокация | Общая сквозная клиентская цепочка в текущем обзоре не подтверждена | Проектировать адаптеры и проверить имеющиеся реализации перед кодом. Workspace-почта лаборатории не равна Gmail каждого клиента |

Допроверка голосового ввода, изображений, Gmail и календаря приведена в
разделе 12: найденные STT/OCR переиспользуем, но не выдаём за готовое
постоянное файловое хранилище.

Эта карта подтверждает наличие кода, не успешную работу всех веток в
production. Полная готовность регистрации/верификации, файлов и подключения
Gmail остаётся отдельной проверкой контрактов до реализации, без платных
операций.

## 3. Схема взаимодействий

```text
Существующее приложение: Chat / карточки / разрешения
            │ существующая идентификация пользователя
            ▼
Chat API: диалоги, сообщения, черновики, чтение после переподключения
            │
            ▼
Диалоговый управляющий слой
   ├── сборщик разрешённого контекста
   │      ├── подтверждённые карточки и контакты
   │      ├── нужные фрагменты документов с источником
   │      └── выбранная история и результаты инструментов
   ├── предложение изменения памяти → подтверждение пользователя
   └── реестр разрешённых операций → серверная проверка → подтверждение действия
                       │
          общие бизнес-операции без дублирования
          ├── план Hint → существующее хранилище → исходящий звонок владельца
          ├── поручение Секретарю → существующее выполнение → результат
          ├── поиск / геолокация / Gmail: отдельные адаптеры и разрешения
          └── календарь / задачи: будущий этап
                       │
        сохранённое событие результата → исходный чат → уведомление

Внешний ChatGPT → собственный существующий вход и полномочия
               → те же бизнес-операции, планы и поручения
```

Не заставлять встроенный чат проходить через внешний ChatGPT OAuth.
Выделить/переиспользовать общий прикладной сервис под обоими транспортами.
Схема не даёт общему чату нынешние owner-only права плагина: доступность каждой
операции проверяется по пользователю, номеру, подключению и действию.

## 4. Единая память и модель хранения

Рекомендуется расширять текущую реляционную модель, а не переносить её в
новую базу. Имена новых сущностей ниже — предложение, не созданные таблицы.

| Сущность | Назначение и основной контракт |
|---|---|
| Существующий users | Идентичность и разрешённые настройки; не хранилище всей беседы |
| Существующие knowledge_cards | Стабильные ID карточек человека и направлений деятельности. Чат и старые экраны обращаются к тем же карточкам |
| CardRevision, новое | Версия содержимого карточки: именованные сведения, источник, кто и когда подтвердил, previousRevision. У карточки одна текущая подтверждённая версия; старое body остаётся совместимым представлением, не второй независимой истиной |
| MemoryProposal, новое | Предложение создать/поменять/отозвать сведения: целевой объект, ожидаемая версия, источник и состояния proposed/accepted/rejected. До принятия не входит в подтверждённую память |
| Существующий contact_memory | Контакты и история отношений. Полевая provenance/подтверждение добавляются совместимо; не дублировать контакты в «памяти чата» |
| Conversation, новое | Пользователь, ID диалога, заголовок, состояние, порядок сообщений, даты. Новый чат не уничтожает общую подтверждённую память |
| Message, новое | Роль, тип, текст/части, clientRequestId, состояние отправки, sequence. Показанные, отменённые и прерванные ответы различимы |
| ObjectReference, новое | Связь сообщения с карточкой, её версией, планом, поручением, звонком или результатом. Карточка в UI — ссылка на объект, а не спрятанный JSON, которому надо верить |
| Attachment, новое или адаптер существующего | Пользователь, источник, безопасный storage key, тип, размер, hash, состояние проверки/извлечения. Файлы отдельно от сообщения; извлечённый текст — производные данные |
| ConversationSummary, новое | Производная сводка с границами сообщений и источниками. Нельзя самостоятельно повышать её содержимое до подтверждённой памяти |
| ContextManifest, новое | Перечень ID/версий и разрешённых полей, реально переданных для конкретного поручения; нужен для объяснения и диагностики |
| Existing plan/task/call | Единственные доменные планы, поручения и звонки; не копировать их состояние в самостоятельные chat_tasks |
| OperationRecord и DeliveryEvent, новое | Запрос инструмента, idempotency key, точный предмет согласования, результат/unknown; долговечная доставка статуса в исходный диалог |
| ExternalConnection, адаптеры | Владелец подключения, scopes, провайдер, статус/отзыв. Credentials только на сервере, никогда в сообщениях/памяти/модельном контексте |

### Карточка пользователя, а не анкета профессии

«Моя карточка» — представление разрешённых данных пользователя и его карточек,
а не ещё одна параллельная биография. Направления деятельности — необязательные
карточки: человек может одновременно водить грузовик, заниматься массажем и
искать работу программистом. Задача может вообще не относиться к профессии.
Существующий personal/work — граница доступа, не классификатор профессий.

### Совместимость старых карточек

В первой фазе не переписывать автоматически body существующих карточек и
не менять контекст живого Hint. При добавлении версий сохранить ID и original
содержимое, отобразить источник legacy и предложить проверку пользователю.
Переход к канонической подтверждённой версии требует адаптации ВСЕХ путей
записи, включая старый редактор карточек. Иначе body и структурированное
содержимое разойдутся.

После перехода запись принятой версии, указателя текущей версии и совместимого
body должна быть одной транзакцией. Любое обновление сравнивает expectedRevision;
конфликт требует перечитать изменения, не затереть сведения.

### Что означает подтверждение

Различать:
- слова пользователя в сообщении — источник для предложения;
- документ, сайт или письмо — сведения источника, не инструкция системе;
- извлечённая моделью гипотеза — proposed;
- явное сохранение/редактирование пользователем — подтверждённое изменение;
- сведения результата звонка — доказательства о звонке, не автоматическое
  изменение личной карточки.

Подтверждение факта не означает разрешение раскрыть его собеседнику.
Разрешение раскрытия задаётся отдельно для плана и профиля.

## 5. Просмотр, исправление и удаление памяти

В «Моя карточка / Что я помню» показывать сведения, источники, статус,
область применения и дату подтверждения. Есть действия исправить, не
использовать и удалить. Новое противоречие вызывает предложение «раньше
было X, сохранить Y?», а не молчаливую замену.

Удаление факта не равно удалению чата; удаление чата не равно отмене уже
сделанного звонка или события во внешнем календаре. Это должны быть
раздельные понятные действия.

Предлагаемая семантика удаления:
1. Сразу исключить удалённый материал из нового контекста и поиска.
2. Удалить/очистить соответствующие payload и старые версии, извлечённые
   фрагменты, производные сводки и кэш; оставить минимальную техническую
   отметку без удалённого текста, чтобы он не «вспомнился» заново.
3. Явно сообщить, если материал ещё присутствует в сохранённой переписке,
   файле или снимке плана. Дать отдельный управляемый способ удалить эти
   копии; не обещать полное удаление, пока они сохранены.
4. Не менять молча отправленный во внешний сервис план и не обещать удалить
   данные, уже переданные третьим лицам. Незавершённые действия повторно
   проверяют актуальность разрешений и сведений перед выполнением.
5. Сроки хранения переписки, файлов, аудио, технического аудита и резервных
   копий согласовать отдельно. Не вводить бессрочное хранение по умолчанию
   и не обещать мгновенную очистку резервов без выбранной политики.

Удаление и каскадная очистка здесь — будущие функции для согласования;
в исследовании никаких данных не удаляли.

## 6. Как передавать контекст

Для каждого сообщения/поручения сборщик контекста:
1. Проверяет пользователя, personal/work, права на документы и операции.
2. Берёт текущий диалог, короткую проверяемую сводку и последние нужные
   сообщения. Длинную историю не загружает целиком.
3. Выбирает относящиеся к задаче принятые карточки/поля и конкретные фрагменты
   документов/контактов. Не отправляет всё резюме для запроса цены шины.
4. Явно помечает предложенное, противоречивое, устаревшее и неизвестное;
   в ownerFacts плана попадают только подтверждённые разрешённые факты.
5. Формирует ContextManifest с версиями и источниками, затем общий CallPlan.
6. Проверяет лимиты существующих инструментов до подтверждения. В частности,
   текущий secretaryInstruction имеет лимит 2000 символов; не обрезать план
   незаметно и не считать лимит компактного промпта Кати лимитом этого API.
7. Перед исполнением повторно проверяет полномочия и hash согласованного
   плана. Изменился бюджет, адресат или запрет — требуется новое согласование.

Для первого этапа достаточно фильтрации по владельцу/профилю/меткам и
полнотекстового поиска. Векторный поиск — возможное последующее дополнение,
не источник истины и не основание откладывать память. Кэш контекста зависит
от ревизии памяти/разрешений и инвалидируется при отзыве или удалении.

## 7. Сохранение, выполнение, восстановление

- Пользовательское сообщение сначала надёжно сохраняется, затем начинается
  ответ модели. Повтор передачи использует тот же request ID.
- Потоковый ответ имеет draft/streaming/completed/interrupted, чтобы после
  перезапуска не показывать незаконченное как законченный вывод.
- Подтверждение содержит объект, версию/hash, адресата и вид действия; это
  не модельный аргумент approved=true.
- Нажатие «Передать Секретарю» вызывает существующее выполнение с его
  защитой от повторного запуска. Общий OperationRecord не подменяет
  существующий clientRequestId или очередь.
- Результат операции и событие для UI записываются долговечно. Если новая
  доставка события неатомарна с существующим callback, согласовать
  reconciler по сохранённым task/call IDs, который только восстанавливает
  доставку, но никогда не повторяет звонок.
- Закрытый чат/приложение не теряет результат. После входа клиент получает
  события после последнего sequence; push — лишь уведомление о них.
- Unknown означает «проверить статус исходной операции», не «запустить с
  новым UUID». Возобновление потока сообщений не запускает инструмент.
- Изменение факта или бюджета создаёт новую версию черновика. Исторический
  снимок завершённого звонка самопроизвольно не меняется.

## 8. Внешние сервисы и клиент

**Gmail, первая версия:** персональное подключение пользователя, минимальные
права по отдельным функциям, статус connected/reconnect/revoked. Чтение и
создание черновика отделены от подтверждённой отправки точного письма
получателю. Вложения/письма недоверенные. После отзыва немедленно прекратить
доступ и инвалидировать связанный контекст. Текущую лабораторную почту не
использовать как общую клиентскую учётную запись.

**Интернет-поиск, первая версия:** серверный адаптер, источники/время
результатов, ошибка и неизвестное вместо выдуманного ответа. Результат
поиска не исполняет команды, не подтверждает наличие/цену без проверки и
не сохраняется в личной памяти без согласования.

**Геолокация, первая версия:** явное разрешение, актуальность и точность
координат, ручной город/адрес при отказе. Передавать сервису поиска только
необходимую точность; не вводить постоянное фоновое слежение.

**Календарь, второй этап:** сначала использовать/проверить существующую
персональную связь рабочего номера, не workspace-коннектор. Общая
запись события потребует отдельного контракта, часового пояса, согласования,
проверки конфликтов и надёжного подтверждения сохранения. Место в боковом
меню сейчас не должно утверждать «встреча добавлена».

**Голос и документы:** голосовой ввод — запись сообщения с разрешением,
транскрипция с исправлением текста до отправки; это не постоянный скрытый
микрофон и не новый голосовой звонок. Для файлов — разрешённые форматы,
предел размера, проверка, извлечение, состояние обработки и контролируемая
доставка в контекст. Крупные файлы не держать в строке сообщения.

**Навигация:** Hint / Translator / Chat / Secretary / History; боковое меню
по согласованному макету. Задачи и календарь пока будущие разделы, проекты
не добавлять. Подписи следуют iPhone; модель может общаться на выбранном
пользователем языке без смены системного языка. Не встраивать чужой
ChatGPT-интерфейс и не обещать импорт его истории/подписки.

## 9. Последовательность и критерии

## 10. Риски и решения до кода

1. **Старые редакторы против новой памяти.** Нужна единая операция записи
   принятой версии; иначе старый PUT перезапишет новые сведения.
2. **Забывание против исторического доказательства.** Уточнить интерфейс
   удаления и сроки хранения снимков/переписки; неизменяемая история не
   должна стать оправданием бессрочного хранения личных сведений.
3. **Два входа к одному инструменту.** Не использовать owner-only scopes
   плагина для обычного пользователя; общий доменный сервис и разные входы.
4. **Доставка результата.** Push и WebSocket могут теряться; нужна
   восстанавливаемая доставка из базы, не повтор действия.
5. **Контекст и ограничения API.** Извлечение лишнего ухудшает приватность,
   обрезка — точность; до выполнения показывать конфликты и неизвестное.
6. **Статус старых модулей.** Карта по исходникам не доказывает настройку
   production, готовую загрузку файлов или Gmail для клиентов. До
   реализации проверить конкретные контракты и конфигурацию без звонков.
7. **Сохранение боевого поведения.** Новый чат не меняет модель, Merritt,
   IVR, таймеры и промпт Кати; существующие планы и история остаются доступны.

Для согласования: принять ли предложенный переход карточек к версиям;
выбрать понятную политику удаления/хранения; определить границу первоначальных
прав Gmail. Финансовые исследования для этих решений не требуются.

## 13. Минимальные технические контракты будущей реализации

Все имена и операции ниже предложены, не созданы.

### Владение, индексы и связи

- Conversation: id, userId, nextSequence, createdAt, updatedAt, state; индекс userId + updatedAt + id. Message: id, userId, conversationId, sequence, clientMessageId, role, parts, state, createdAt; уникальны userId + conversationId + sequence и userId + conversationId + clientMessageId. Ссылки проверяют пару owner + objectId, а не только глобальный UUID.
- CardRevision: cardId, userId, revision, structuredContent, sourceRefs, confirmedBy, confirmedAt; уникальна пара cardId + revision с проверкой владельца. KnowledgeCard хранит указатель acceptedRevision. MemoryProposal хранит expectedRevision и proposedContent; принятие выполняется транзакционно compare-and-swap.
- ObjectReference связывает messageId с типом доменного объекта, objectId и snapshotRevision/hash. Историческая карточка показывает согласованную версию, а не незаметно обновлённый текст. Ссылка на текущую версию обозначается отдельно.
- ContextManifest хранит ссылки/версии и разрешённые поля, а не копию всех документов. Полный переданный снимок хранить только при явно согласованной необходимости и сроке хранения. Для удаления достаточно отслеживаемых зависимостей, а не поиска по догадке.
- OperationRecord: userId, conversationId, operationId, requestId, tool, targetRef, inputHash, approvalRef, state, domainResultRef. Уникален пользователь + tool + requestId; другой payload с тем же requestId возвращает конфликт. Создание новой записи операции никогда не означает автоматический повтор телефонного действия.
- DeliveryEvent: eventId, userId, conversationId, sequence, type, objectRef, deliveryState; повтор источника дедуплицируется по sourceType + sourceId + sourceRevision. Статус карточки читается из существующего task/call, не из независимого chat-статуса.
- Attachment: owner, storageKey, mediaType, size, hash, scanState, extractionState, lifecycleState; раздельные временные ссылки на скачивание. Signed URL, OAuth tokens и keys не являются ни памятью, ни полями модели.

### Состояния и параллельность

- Ответ: accepted → generating → completed / interrupted / failed. Разрыв SSE не считается разрешением новой генерации; клиент перечитывает сохранённое operationId. Несохранённые промежуточные токены можно потерять, но нельзя выдавать их за завершённый ответ.
- Память: proposed → accepted / rejected / withdrawn; принятая карточка получает новую revision, предложение сохраняет ссылку на принятую версию. Конкурирующая правка с устаревшей revision получает конфликт.
- Действие: draft → awaiting_confirmation → authorized → executing → succeeded / failed / unknown. Серверное согласование связано с exact target, hash и версией. При отказе, истечении или изменении черновика выполнение не начинается.
- Внутри транзакции БД не держать внешний модельный или телефонный HTTP-запрос. Сначала записать локальное намерение/lease; после неизвестного ответа разбирать статус исходного действия. Outbox/reconciler повторяет доставку, а не само действие.
- Новые сервисы переписки и памяти не должны сообщать «сохранено» при fallback в Map или при undefined из текущего storage. Подтверждение клиенту только после COMMIT, при недоступной БД — явная ошибка.

### Будущий API, не реализация

- POST /api/chat/conversations, GET /api/chat/conversations, GET /api/chat/conversations/:id/messages с cursor; прежний POST /api/chat пока не заменяется.
- POST /api/chat/conversations/:id/messages принимает стабильный clientMessageId; чтение событий возобновляется после sequence.
- GET /api/chat/memory возвращает только собственную память, источники и состояния; POST /api/chat/memory/proposals/:id/accept требует expectedRevision и реальное действие пользователя.
- Подготовка и подтверждение операций — разные серверные действия; восстановление существующей операции по ID только читает статус. Read/prepare/execute реализуются с разными политиками, не одной всесильной модельной функцией.
- Любой web-вход с cookie защищается от CSRF/чужого Origin; native использует существующий Bearer. userId берётся из аутентификации, не из тела запроса. Существующий внешний ChatGPT OAuth остаётся отдельным транспортом.

### Совместимость памяти с живыми инструментами

Существующие knowledge_cards читаются и вне чата, в том числе как статический контекст Hint. Новые личные карточки не должны автоматически попасть в каждый звонок. Перед созданием новых видов памяти нужны адаптеры ВСЕХ читателей и писателей: default chat-only для новых сведений, прежний доступ для существующих одобренных карточек, раскрытие в звонке только через разрешённый план/профиль. Не подменять legacy cardType обязательной профессией. Детальный способ расширения DTO и категорий принять до миграции.

Миграция поэтапная: добавить совместимые сущности → внедрить адаптеры чтения/записи под выключенным rollout → проверить на синтетических данных → отдельное разрешение владельца. Никакого DROP/DELETE в схеме этого этапа. Старые ID, планы и рабочие операции сохраняются; версия клиента не активирует новые права.

Если будущая реализация создаёт таблицу кнопкой или кодом, её схема должна
существовать и в Dev, и в production по отдельно утверждённому порядку.
Перед Publish сверять предлагаемые изменения схемы: пусто или CREATE,
при DROP/DELETE — остановка. Это требование будущего внедрения, не выполненная
миграция в этой задаче.
