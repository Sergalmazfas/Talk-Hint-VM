# P.PRODUCT — журнал, работа в ролях и один связанный пример

Статус: проект изменений на согласовании. Источник — существующая new-country.
Действующий журнал не создан; новые документы модели пока не сохранены.
В полном текущем перечне документов отдельного «Журнала улучшений» не найдено.
Прежние proposals/decisions и документы жалобы не заменяются и не удаляются.

## Единый журнал

Предлагаемый документ: «TalkHint — журнал улучшений», schema v1.
Если до применения появится подходящий документ — использовать его ID вместо нового.
Планируемый ID DOC-TALKHINT-IMPROVEMENT-JOURNAL — резерв предложения, не сохранённая запись.

Один случай объединяет жалобу/находку, а не каждую реплику. Тип:
обратная связь, ошибка, исследование, улучшение или входящая договорённость.
У случая есть действующий ID либо ссылка на существующий call/case, глава продукта,
ответственная роль и хронология; конкурентная находка не становится решением копировать.

Минимальная запись:

- источник, дата самого события, дата обнаружения/регистрации, автор;
- исходное сообщение и факты со ссылками; гипотезы отдельно;
- связанные действия, ресурсы и запросы; кто поставляет недостающий вход;
- результат/версия, принимающее действие, критерии приёмки/возврата;
- решение и основание полномочий; кем и когда принято;
- версия реализации, платформа/сборка/окружение;
- проверка «до/после», ограничение сопоставимости и независимый QA;
- оценка владельца, статус, следующий шаг.

События добавляются, не переписывают прошлое. Статусы жизненного цикла случая
не заменяют независимые признаки «описано / реализовано / проверено / принято / в плане».
Автор результата не заполняет за получателя ответ или приёмку. Случай нельзя
закрыть по SENT, наличию кода, положительному word-count или смене названия роли.

## Как переключаться между ролями

Каждый проход начинается: роль → существующее actionId → caseId →
входные версии → ожидаемый результат → ресурс → получатель/принимающий.
Первой строкой ответа даётся версия реально прочитанных правил и дорога.

При переходе передаются ID случая, версия выхода, конкретный вопрос и доступное
содержимое доказательства. «Источник у меня был» не означает, что он доступен QA.
Нет ресурса/ответа — адресный запрос, статус «ожидает», остальные независимые части
могут продолжаться. Исполнение тем же Replit двух ролей явно маркируется;
оно не заменяет независимого проверяющего. Отдельного сотрудника не выдумывать.

Перед новой работой перечитать ревизию. По завершении — сохранённый результат,
передача, фактический ответ либо ожидание. Новый JSON берётся из той же модели;
ручной протокол хранится отдельно от исходной инструкции.

## Один пример: жалоба кофейни

Используется существующий HINT-OWNER-FEEDBACK-001, не вторая жалоба.
Канонические источники:

- DOC-HINT-OWNER-FEEDBACK-001 v2;
- DOC-HINT-FAST-DIALOGUE-FACTS v1;
- DOC-HINT-COFFEE-DIAGNOSTIC v1;
- DOC-TALKHINT-CHAPTER-HINT v3;
- DOC-TALKHINT-PRODUCT-PASSPORT v12.

Цепочка с точными существующими actionId/resultId и состояниями сохранена в
`journal.proposed.json` из полей steps исходной жалобы. Это реконструкция
сохранённого состояния, НЕ новый прогон и не новые решения.

1. P.PRODUCT уже зафиксировал жалобу и передал P.LAB.
2. P.LAB дал факты по трём звонкам; звук и полная аудио/UI-проверка отсутствуют.
3. P.LG.TECH, P-BENCH и P.UX — отдельные входы, не обязательная последовательность.
4. Ограниченный текстовый стенд уже выполнен исторически: 18 запросов, 9 пар.
   Compact был быстрее, но перепутал говорящего; это не кандидат на выпуск.
5. Независимая QA стенда и решение владельца ожидаются. Отдельный диагностический
   разбор кофейни завершился LAB_ANALYSIS_FAILED; новое письмо не отправлялось.
6. Продуктовая записка существует; правильное следующее действие — принять
   проверяемый результат либо вернуть конкретные замечания, не объявить улучшение.
7. В план-факт попадают раздельно: исследование выполнено; акустический стенд
   заблокирован; QA/решение не получены; продуктового внедрения по жалобе нет.

## Первые записи и изменения Hint

Два Mint связываются по прежним callSid и исходному документу фактов.
Дата Mint 26.10 Denver отличается от UTC 27.10: это не четвёртый звонок.
Кофейня использует прежний ID жалобы. Отдельная предлагаемая запись про ручное
скрытие первой фразы ссылается на исходники iOS; наличие метода не доказывает
проверку конкретной установленной сборки. Оценка владельца изменения — «ждёт».

Для каждого следующего принятого изменения: дополнить тот же случай, затем
сослаться из существующей главы/книги и единого roadmap; не копировать полный
журнал во все главы. Версии повышаются только при действительном сохранении.

## Передачи и отчётность

- Факты лаборатории → существующая приёмка продукта.
- Вопрос «почему так в коде» → HEAD.07/существующий технический специалист.
- Контроль зависания/отсутствия передачи → P.OPS, не пересмотр QA.
- Дневной вклад → существующий T07.REPORT.DAY; недельный/месячный —
  T07.REPORT.WEEK/MONTH, затем прежняя общая сводка.
- Бланки и карта покрытия принадлежат прежнему P.OPS:
  DOC-POPS-WORK-PACKAGE и DOC-POPS-DAILY-REPORT.
  В этом документе их копий нет; см. `links.html` и `ops.proposed.patch.json`.
