# AI Crew · механизм запуска · пакет на независимую проверку

## Границы этапа

Это механизм, а не включение сотрудников. Нет записи в `production/new-country`,
нет включённых агентов, изменённых личностей или настроек Кати, звонков, удаления,
Publish, Archive или TestFlight. Рекомендации моделей в анкетах не активируются.

Серверный диспетчер работает только в production. Начальное состояние:
`enabled=false`, общий дневной лимит `0`, срок зависания `24` часа,
нет назначенных агентов, событий или расписаний. В Dev диспетчер не запускается.

## Где находятся задачи и результаты

Отдельная таблица PostgreSQL `ai_crew_runtime_state`, строка на среду.
Это **не** редактор модели компании и не хранилище знаний сотрудников.
В одной транзакции с блокировкой строки сохраняются управление, очередь,
резервы бюджета, задачи, описательные предложения и журнал.
История не удаляется и не обрезается. Это сознательно простой первый этап;
при росте объёма потребуется отдельный согласованный переход на нормализованный журнал.

Владелец создаёт задачу (`task`), передаёт её в `analysis` (`advance`).
После отдельного будущего решения о запуске он задаёт модель/тариф агента,
назначает событие с UUID (`enqueue`) либо расписание (`schedule`).
Production worker проверяет очередь каждые 15 секунд.
Никакие реальные звонки автоматически в очередь не добавлены.

Агент получает только текст назначенной задачи, фиксированные ограничения и
описание текущего разбора. У него нет tools, shell, доступа к MCP-записям,
продуктовым таблицам, звонкам, промптам, настройкам или публикации.
Единственный результат — документ `status=proposed` и запись расхода в журнале.
Предложение не считается принятым знанием и само не переводит задачу на следующий шаг.
Передача результата лаборатории проверяющему и решения владельца фиксируются
в журнале владельцем; автоматическую оркестрацию конкретных сотрудников этот этап не включает.

## Выключатель и деньги

Одна долговечная настройка владельца `control.enabled` действует на все назначения.
Аварийное отключение не требует актуальной UI revision: оно выключает флаг и
меняет epoch в БД, затем прерывает локальный transport. Другой процесс проверяет
epoch раз в секунду; результат после выключения не сохраняется как предложение.
Новый вызов не резервируется при выключенном флаге или нулевом лимите.
Сбой записи выключателя возвращает ошибку, а не ложный успех.

Все агенты используют один бюджет по **UTC-дню**. Суммы — целые microUSD:
1 USD = 1 000 000 microUSD. Перед запросом транзакционно резервируется
консервативная стоимость UTF-8 input + запас framing + индивидуальный максимум:
Паша/прочие роли 2000, Фома 4000 output tokens, включая thinking Opus.
Нет tools или prompt caching.

Тарифы не угадываются и не берутся из маркетингового названия модели.
До запуска владелец должен отдельно утвердить консервативные ставки
input/output за токен и точный API ID. Значения в запросах к моделям сейчас не заданы.
Учёт `usage × зафиксированный тариф` — внутренний учёт, **не счёт Anthropic**.
При timeout, abort или сбое после отправки резерв остаётся занятым,
статус `unknown`, платный запрос автоматически не повторяется.
При неожиданном превышении резерва учитывается фактический usage и механизм
выключается. Изменение тарифа не пересчитывает прежние записи.
Внешние тарифы/инвойс и абсолютная точность денежных оценок до утверждения ставок
не подтверждены; включать исполнителей по этому пакету нельзя.

## Шесть шагов

1. `problem`: проблема, держатель.
2. `analysis`: лаборатория и независимый проверяющий; один и тот же участник
   не может быть записан в обе роли.
3. `owner_decision`: решение владельца и обязательное ожидание.
4. `code`: что изменено, держатель-инженер, обязательный commit.
5. `verification`: обязательная проверка именно записанного нового commit.
6. `outcome`: сохранённое ожидание / полученный факт. Совпало — закрыто,
   не совпало — новая запись `analysis` с сохранением всей прежней истории.

У каждого шага есть держатель и дата последней записи. Статус зависания вычисляется
по последней записи задачи, порог по умолчанию 24 часа. Уведомления/рассылка
о зависании на этом этапе не подключены. Все переходы — только через owner endpoint;
модель не одобряет решения, не закрывает задачи и не принимает свою работу.
Журнал проверяет заполненность и согласованность переданных доказательств;
он не подменяет независимую проверку, GitHub или реальную сборку на Mac.

## Публикации и звонки

`docs/releases/current.json` — ссылка на задачу дорожной карты и описание исправлений
для текущей публикации. Перед **каждым будущим Publish** обновлять этот manifest под
реальную задачу; не оставлять описание данного этапа для посторонних изменений.
Сборка встраивает commit, признак незакоммиченных изменений, hash исходников,
дату сборки и manifest. После появления таблицы production-сервер один раз
записывает `publication_observed` для каждой сборки. Повторный запуск того же
build не дублирует запись; новый build того же исходного кода фиксируется отдельно.
При недоступной БД запись откладывается до восстановления, не выдумывается.
Владелец также может связать публикацию с задачей журнала через `publication`:
нужны ID задачи, ранее записанный инженерный commit и описание исправлений.

Новые записи звонков получают версию кода **при создании**. Замена metadata
сохраняет исходную метку. Hint, уведомления других режимов и письма лаборатории
показывают сохранённую версию звонка. У старых звонков без метки — «неизвестна»,
не текущая версия анализа. В обычные metadata не попадают внутренние описания
исправлений и ссылки на задачи. Маршрутизация/голос/меню Кати не менялись.
Проверка новыми реальными звонками в этот этап не входит.

## Anthropic

Наличие `ANTHROPIC_API_KEY` в **конфигурации production secrets** подтверждено
через метаданные без доступа к значению. Это не доказательство успешного inference
в опубликованном процессе.

Неплатное чтение `GET /v1/models` из Dev фактически вернуло:
`claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-5-5`.
Полный ответ без ключа — в `model-catalog.json` приёмочного ZIP.
Идентификаторы не угаданы. Список из production нужно подтвердить после Publish.

Подготовлен owner-only одноразовый production probe: фиксированное «Reply only OK»,
не больше 8 output tokens, никаких агентов. Выбор ID только из свежего ответа API.
Слот probe занимает транзакционно **до** отправки; после неоднозначного ответа
повтор запрещён. Сохраняются только model/usage/status, не ответ и не ключ.
Это отдельно разрешённая диагностическая операция, не запуск агента при бюджете 0.
Сейчас probe **не выполнен**: опубликованный код ещё не содержит этого endpoint.

Официальные контракты:
- https://platform.claude.com/docs/en/api/models/list
- https://platform.claude.com/docs/en/api/messages

## Защита

Весь интерфейс и API закрыты существующим owner/admin allowlist.
POST требуют существующую Origin-защиту и session CSRF; аутентифицированный Bearer
остаётся отдельным не-cookie способом в пределах той же owner-проверки.
CSRF не даёт прав без авторизации. UI не предлагает включение агентов.
Данные API выводятся через textContent, не как HTML.
Провайдер имеет фиксированный адрес, redirects запрещены, timeout ограничен.
Ошибки наружу — фиксированные коды, без сырых ответов провайдера и заголовков.
API key не сохраняется в таблице, документах, Git или отчёте.
