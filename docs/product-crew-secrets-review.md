# Production Product Crew MCP — Secrets fallback, security review

## Решение и фактический статус

Владелец разрешил основной вход Dev-скриптов в production MCP через
`PRODUCT_CREW_KEY` и заголовок `X-API-Key`. OAuth и ручной 90-дневный ключ
остаются запасными способами. Полномочия не расширяются.

**Код готов к независимой сверке, но настройка не завершена.**
На проверке наличия секрет `PRODUCT_CREW_KEY` отсутствовал. Доступный агенту
защищённый механизм умеет запросить значение у владельца, но не генерировать
и сохранять его скрыто в Project Secrets и Production app secrets.
Реальный ключ не генерировался, не запрашивался и не записывался в обход
этого механизма. Обещание «один Publish, больше ничего» не выполнено.
Нельзя объявлять этот пункт завершённым по одному наличию кода.

Не использовать `setEnvVars`, файлы `.env`, Git, отчёты, логи или чат для ключа.
Для конфигурации требуется защищённое сохранение одного криптостойкого значения
(не менее 32 случайных байт, например base64url из 32+ байт) под именем
`PRODUCT_CREW_KEY` в обе среды. Значения не читать и не сравнивать выводом.
Это должен быть отдельный новый секрет, не копия ручного запасного ключа:
два способа входа не должны использовать одну и ту же строку.

Документация Replit:
- https://docs.replit.com/core-concepts/project-editor/app-setup/secrets
- https://docs.replit.com/build/code/adding-secrets-to-environments

## Изменения

- `server/productCrew/secretKey.ts`: сравнение SHA-256 через `timingSafeEqual`;
  допустимый секрет — ASCII base64url/hex-совместимая строка 43–512 символов.
  Формат не доказывает случайность: значение должно создаваться CSPRNG.
  Ни `status`, ни ошибки не возвращают секрет или hash.
- `bootstrap.ts`: провайдер получает секрет из окружения **только** в
  production, с production-базой и существующим фиксированным владельцем.
- `routes.ts`: при совпадении секрета используется новый проверяющий,
  иначе остаётся ручной ключ. Выключенный совпавший секрет не получает
  fallback. Одновременные `Authorization` и `X-API-Key` запрещены.
- Общие `authorizedOwner`, `ProductCrewService`, production repository,
  `new-country`, CAS/revision/requestId, блокировка записи и запрет
  `review_result` остаются прежними. Нет новой поверхности звонков,
  денег, Publish, удаления, секретов или приёмки за владельца.
- GET `/api/admin/product-crew/owner-key` дополнен `secretStatus`:
  `configured`, `disabled`, `lastUsedAt`. Значение/отпечаток не выдаются.
- POST `/api/admin/product-crew/owner-key/disable-secret`:
  браузерная сессия фиксированного владельца + действующий allowlist,
  точный Origin, одноразовый CSRF, JSON `{confirm:true}`.
  Доступ по ключу или OAuth сам себя администрировать не может.
- Страница https://talkhint.app/admin/product-crew-key показывает статус,
  дату использования и кнопку «Отключить». Нет поля ввода Secrets-ключа,
  показа значения, повторного включения, автоматического повтора.
  При неоднозначном ответе сначала явное повторное чтение.

## Хранение и отзыв

Новых таблиц и миграций нет. Используется существующая таблица credential
markers `sessions` с отдельным namespace `productcrew:secret-*`.
В ней только hash ключа/владельца в идентификаторе, владелец и даты.

Проверка ключа и отключение сериализованы транзакционной advisory-блокировкой
на владельца/hash, в том числе между workers. Нет кэша разрешения:
следующий запрос после успешного отключения запрещён.
Уже допущенный запрос не отменяется задним числом.

Маркеры отключения и last-used имеют технический срок 9999-12-31:
обычная уборка истёкших сессий не должна незаметно оживить отозванный секрет.
Это не изменение хранения бизнес-данных модели. Last-used — время успешной
аутентификации, не доказательство успешной записи или приёмки.

Замена: новое значение в обеих защищённых средах + Publish.
Новый hash — новый доступ и новая дата использования; возврат старого
отключённого значения не снимает отзыв. Автоматического срока 90 дней
у Secrets-ключа нет: 90 дней остаются только у ручного запасного ключа.
Отзыв ручного ключа не отключает Secrets/OAuth и наоборот.

## Dev-клиент и проверка после Publish

`script/product-crew-production-mcp.mjs` берёт значение только из
`process.env.PRODUCT_CREW_KEY`, отправляет его только на фиксированный
https://talkhint.app/api/product-crew/mcp, запрещает redirect,
имеет timeout 15 секунд на запрос и чтение JSON, не делает retries,
не выводит сетевые ошибки или ответы, содержащие значение ключа.

Команда агента **после** подтверждённой настройки Secrets и Publish:

    node script/product-crew-production-mcp.mjs

CLI не принимает аргументы и выполняет только `tools/list`, `get_team`,
`get_roadmap`. Проверяет наличие инструментов, отсутствие `review_result`,
целую совпадающую ревизию двух чтений. Выводит endpoint, production,
new-country, названия инструментов, ревизию и число ролей — не секрет.
Production/new-country обеспечивается серверной изоляцией, не произвольным
параметром запроса. Для последующей разрешённой работы есть экспорт
`callProductionMcp`; текущая проверка ничего в модель не пишет.

После успешного реального чтения можно продолжать уже порученные отдел кадров
и этап «Команда Hint» через тот же MCP, с повторным чтением каждого изменения.
Это не запуск автономных сотрудников и не приёмка за владельца.
Никаких записей модели в этом diff не делалось.

## Что проверить Claude

1. Нет plaintext-персистенции, секретных значений в ответах/ошибках/логах;
   сравниваются digest фиксированной длины, а не строки ключей.
2. Secrets-путь недоступен в Dev/public MCP, владелец и production DB закреплены.
3. Wrong/missing/disabled ключи отклоняются; отзыв долговечен и fail-closed
   при недоступной БД; действующий allowlist проверяется на каждом запросе.
4. Origin/CSRF/session/confirm для отключения не слабее ручного ключа;
   повтор запроса не повторяет операцию.
5. Закрытая запись остаётся закрытой; чужая модель и полномочия владельца
   не доступны; OAuth/ручной ключ не отзываются отключением Secrets.
6. Dev-клиент не пересылает header при redirect, не принимает URL override,
   не печатает секретные ответы и не повторяет неоднозначные записи.
7. Конфигурационный блокер не замаскирован под готовый живой доступ.

## Границы доказательств

Результаты текущих тестов/сборки — в `verification.md` и приложенных логах.
Браузер — реальный React-компонент с изолированным тестовым API; это
не реальный вход владельца, не Safari iPhone и не production-соединение.
На настоящем preview без входа остаётся защищённый экран входа.
Реальный `tools/list/get_team` и production-ревизия ещё не проверялись.

Независимый вердикт Claude не получен. Publish выполняет владелец после сверки.
Галочку копирования Dev в production не ставить. iOS не менялся.
