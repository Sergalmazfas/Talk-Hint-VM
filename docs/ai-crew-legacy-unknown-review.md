# Клавдию · разовое списание по решению владельца + structure check

Этот документ заменяет неопубликованный план общей изоляции unknown.
Владелец утвердил списание конкретного старого запуска и разрешил параллельную
сверку Клавдия, не ожидая её для Publish после зелёных тестов.
Production в этом этапе не меняется; Publish выполняет владелец.

## Минимальный контракт

В существующем отдельном crew-test MCP появляется восьмой инструмент:
`crew_test_writeoff_legacy_unknown`.
Аргументы: `revision`, новый UUID `requestId`,
`command: {"action":"writeoff_legacy_unknown"}`.
Никаких taskId, runId, суммы, force или произвольного решения от клиента.

На сервере зафиксированы:
- taskId `efa4e3d5-e5cf-4177-b10f-4943e71775f1`;
- ровно один запуск этой задачи: Паша, status=unknown;
- ровно 36 716 microUSD = $0.036716;
- итог дословно: «не выполнено: прерван аварийным OFF».

Права только отдельного CREW_TEST_KEY/crew-test с действующим 7-дневным grant,
отзывом, общим $5 на серию. Без сессии владельца или расширения PRODUCT_CREW_KEY.
Новой кнопки нет. Нового подтверждения решения владельца не требуется.

OFF обязателен, running нигде быть не должно. Задача legacy latency в
analysis/author, не закрыта, не относится к тест-серии; нет документов,
proposal/review, usage, settled cost. Дневной резерв и общий лимит должны
позволять точный перенос. При расхождении — STOP, не подстановка и не повтор.

## Атомарная запись

1. Дневной budget: reserved -= 36716, spent += 36716. Общая сумма не меняется.
   Чужие резервы, другие дни и расходы не затрагиваются.
2. Series spent += 36716 против общего лимита $5 (та же сумма для второго
   бюджетного ограничения, не второе списание у провайдера).
3. Запуск: status=discarded, reserved=0, cost=36716, completedAt.
   Метаданные явно сохраняют providerOutcome=unknown и owner_emergency_off:
   это решение владельца о списании, не проверенный счёт и не успешная генерация.
   usage не выдумывается. Исходная сумма сохранена в журнале.
4. Задача закрыта, outcome: «не выполнено: прерван аварийным OFF», met=false.
   Старые шаги, journal и владелец задачи не переписываются.
5. Квитанция и append-only журнал actor=replit-test: task/run/series IDs,
   сумма, оригинальный резерв, unknown, ownerAcceptance=false.
6. Никакого запроса провайдеру, приёмки результата, ON или запуска Фомы.

Одна транзакция/CAS CrewStore. Старый/повторный UUID и повтор новым UUID
отклоняются; закрытая задача больше не подходит. Rollback сохраняет обе
стороны денег. Поздний ответ не принимается и не меняет списание.
Любые другие unknown/running продолжают блокировать обычную подготовку.

После записи доступно writtenOffLegacy с квитанцией и дневным budget для
повторного чтения. Расход новой серии после этого $0.036716; остаётся не
более $4.963284 до новых запросов. Включение остаётся отдельной командой.
OFF/0 техническая подготовка после этой квитанции не обнуляет расходы.

## Исправление structure check

По журналам сервер успешно завершал read-only аудит за 35–37 секунд,
клиент обрывал ожидание через 20. Только для crew_structure_check deadline
увеличен до 90 секунд. Для state, tools/list и всех записей остаётся 20 секунд.
Автоповторов нет. Таймаут записи по-прежнему означает STOP.
Серверный аудит/модель компании не менялись; 398 замечаний не объявлены исправленными.

Выделенный scripts/lib/crew-test-rpc.ts позволяет воспроизвести 37-секундное
успешное чтение и проверить лимиты fake timers без ожидания/реальной сети.
Внешняя структура API и права не расширены ради времени ожидания.

## После Publish — уже разрешённая последовательность

1. tools/list → свежее state; сверить OFF и ровно утверждённый запуск/сумму.
2. `npx tsx scripts/crew-test.ts writeoff`: одна запись со свежей revision/UUID,
   повторное чтение, сверка discarded/reserved=0/cost=36716/закрытая задача/OFF.
3. `npx tsx scripts/crew-test.ts structure`: только чтение, bounded 90 секунд.
4. `npx tsx scripts/crew-test.ts latency`: prepare → enable → start,
   отдельные revision/UUID/readback; Паша → Фома → автоматический OFF.
   CLI не закрывает посторонние legacy-задачи и не работает автоматически при Publish.
5. При ошибке или unknown — STOP без повтора; независимый 5-минутный watchdog.
6. Владельцу краткий результат/цена/содержательность; Клавдию ZIP журнала,
   предложения Паши, заключения Фомы. Результат остаётся на приёмку владельцу.

## Проверки и ограничения

Новые/обновлённые тесты: точная задача/сумма, OFF/не running, отказ для
другой задачи/фазы/суммы/прав/резерва/документов; неизменность других денег;
double-click/new UUID/CAS; rollback и рестарт настоящего Dev TEMP jsonb;
поздний ответ; новая mocked цепочка с OFF; прочие unknown не разблокируются.
Клиент: 37-секундный read успешен, >90 секунд отказ; slow write >20 секунд
не повторяется; error ответ не повторяется и не раскрывает приватный текст.

Точная сводка полного набора по шардам приложена в ZIP. Реальных моделей,
production-записей и нового Publish в этом этапе нет. Счёт Anthropic не
проверяется; списание основано на решении владельца. UI за входом не
проверялся визуально, экран не изменялся. Катя/звонки/промпты не затрагивались.
Миграций/новых таблиц нет. Copy development database to production не включать.
