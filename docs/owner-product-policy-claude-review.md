# На сверку Claude: фиксированное правило согласования изменений продукта

## Статус и границы

Это diff и тесты, не приёмка и не разрешение на Publish. Production-модель не изменялась.
Рабочие промпты, исполнители, телефония, модели, провайдеры, деньги и доступы не переключались.
Изменение веб-отображения ограничено показом запретов в уже существующих полях карточек.
Publish, запись production и включение сотрудников не выполняются при проверке этого пакета.

В `replit.md`, §2.1, уже сохранён полный текст решения владельца. Новая серверная константа
должна совпадать с ним дословно; это проверяется тестом. Универсального редактора политик нет.

## Что добавлено

Один MCP-инструмент `apply_owner_product_change_policy`.
Общие обязательные поля: `revision`, UUID `requestId`, `reason`, `ownerDecisionRef`,
`target`, `documentId`, SHA-256 **полного исходного текста** документа в `documentHash`.
Дополнительные поля запрещены, включая `text`, `prompt`, `enabled`, `permissions`,
`executorId`, `hypothesis` и `commands`.

Три разрешённых цели:

1. `company_passport` — только `DOC-TALKHINT-PRODUCT-PASSPORT`.
   Создаёт один документ `DOC-COMPANY-OWNER-PRODUCT-APPROVAL` с фиксированным
   текстом решения. В паспорт записывает только ссылку `ownerProductChangePolicyRef`
   и увеличивает структурную версию. Сохраняет все остальные поля JSON,
   предисловие и суффикс исходного документа. Произвольный текст не добавляется.
2. `ai_crew_rules` — только существующий документ
   `DOC-PC-b57c7c66-12b8-47cc-afe6-651a68e20132`.
   В существующее дополнение паспорта компании добавляет фиксированный текст
   в список правил и ссылку на общий документ. Старые статусы proposed и accepted=false
   не повышает: это не приёмка ранее подготовленных предложений.
3. `employee_profile` — один существующий JSON известных форматов
   `talkhint.employee.profile` или `talkhint.role-prompt-proposal`,
   с непустым `visualPassport.roleId`.
   Добавляет точную строку «не вносит изменения продукта без согласования владельца»
   в корневые запреты и ссылку на правило; увеличивает версию только при изменении.
   Все другие поля, включая личность, промпт, прежние запреты и права, сохраняются.
   Неизвестный формат запретов/версии, чужой формат документа, устаревший hash —
   отказ, а не попытка восстановления.

Перед целями 2–3 требуется корректная связка канонического паспорта с документом правила.
Конфликтующий ранее существующий документ/ссылка не заменяются.
Новый requestId для уже внесённого текста не создаёт дубликаты и не повышает версию анкеты;
обычная сервисная квитанция при этом сохраняется. Тот же requestId воспроизводит квитанцию
без новой записи. Старая revision и изменённое содержимое при повторе отвергаются.

## Как правило видно читателям

- `get_team`: возвращает общий текст правила и `inheritedProhibitions` у каждой роли.
  Неизвестные прежние поля роли не могут подменить этот вычисленный запрет.
- Страница команды: отображает корневые запреты анкеты вместе с прежними.
  После регистрации общего правила все карточки наследуют его, включая планы,
  внешних участников и карточки, добавленные runtime-проекцией Кати.
- Runtime-проекция меняет только данные запретов карточек; телефонный runtime Кати
  и её рабочий промпт не затрагиваются.
- Виртуальная карточка без хранимой JSON-анкеты получает наследуемый запрет;
  инструмент не создаёт ей фиктивную анкету.
- Неизвестные форматы анкет не мигрируются автоматически: их нужно перечислить
  при подготовке production-плана, а не объявлять все документы обновлёнными.

## Почему ссылка, а не копия текста в паспорте

Проверен сохранённый снимок: 49 630 → 49 697 символов при существующем лимите 50 000.
Полный текст вынесен в один нормативный документ. Текст прежнего паспорта не удаляется
и не обрезается. Уплотнение JSON не используется для удаления данных.
Полная операция паспорта: создать правило + сохранить ссылку + сервисная квитанция,
то есть **3 команды**, существующий максимальный размер обычного атомарного пакета.
Лимиты репозитория и специальная семикомандная операция отдела Секретаря не расширяются.
AI Crew и отдельная анкета: максимум 2 команды вместе с квитанцией.
Это не одна атомарная миграция всех сотрудников: подтверждённые записи идут последовательно,
каждая с повторным чтением и остановкой при расхождении.

## Проверки для Claude

1. Дословность решения и невозможность ослабить правило через параметры инструмента.
2. Наследование действующих проверок owner/read-write/production/new-country и закрытой записи.
3. Проверка hash до изменения, отсутствие удаления старых данных и опасных форматов.
4. Атомарность паспорта вместе с квитанцией при существующем лимите 3.
5. Идемпотентность и отсутствие смены промптов, личности, executor, модели и статусов приёмки.
6. Производный запрет у всех карточек, включая финальную runtime-проекцию.
7. Не путать наследуемый запрет с уже выполненной записью всех исходных JSON-анкет.

Команды:

```sh
npm run check
npx vitest run server/productCrew/ownerProductPolicy.test.ts server/productCrew/productCrew.test.ts server/team --maxWorkers=1
npx vitest run --maxWorkers=1
git diff --check
```

Результаты исполнения — в `verification.json` внутри пакета. Проверки репозиторного
лимита используют настоящий `assertTransactionBatch`; сохранённые production-снимки
проверяются только в памяти, без SQL/MCP-записи. Это не доказательство выполненной
транзакции на production-БД. Закрытый экран владельца не проверен визуально под входом.

## После независимой сверки и Publish владельцем

1. Свежие `tools/list` и `get_team`; проверить наличие инструмента и текущую ревизию.
2. Полное чтение паспорта, SHA-256, `company_passport`; затем повторное чтение паспорта
   и фиксированного документа правила, проверка сохранности прежнего содержимого.
3. Полное чтение существующего AI Crew, hash, `ai_crew_rules`; повторное чтение.
4. Полная инвентаризация анкет, включая документы вне графа ролей.
   Каждая поддерживаемая анкета: чтение → hash → одна запись → повторное чтение.
   Для виртуальных карточек отдельно проверить наследование; неизвестные форматы —
   остановка и отчёт, без обхода.
5. Не повторять запись вслепую при неоднозначном ответе.
6. Приёмку выполняет владелец/независимый проверяющий, не инструмент и не исполнитель.
