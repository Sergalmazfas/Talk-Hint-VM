## Согласованный порядок записи — остановлен на свежем tools/list

1. Свежие `tools/list`, `get_team`, чтение трёх исходных анкет и
   `DOC-SECRETARY-DEPARTMENT-STRUCTURE`; hash, revision и сверка форматов.
   Только чтением уточнить реальные ID личности, книжки и промпта Кати.
   Не заполнять ссылки каталога, не создавать источники по догадке.
   При несовпадении — STOP, без повторной записи.
2. По одной существующей роли: `update_role_passport` для согласованного
   описания обязанностей, входов, результатов, ограничений и приёмки.
   Не добавлять исполняемые action-узлы и расписания.
3. `update_employee_sections` — рабочее место, согласованная рекомендация
   модели выше и `repairReportsTo` по существующему графу, с hash свежей анкеты.
   Порядок по одной роли: паспорт → повторное чтение → разделы → повторное чтение.
4. Для каждой записи — свежая revision, hash и сверка ожидаемого состояния,
   новый UUID, подтверждение, повторное чтение и точный ожидаемый diff.
   По текущему контракту `update_role_passport`: 1 команда saveElement,
   UUID в operations, без отдельной квитанции. `update_employee_sections`:
   2 команды (документ + квитанция PC-CHANGE). До отправки сверить контракт,
   после — фактический ответ и revision повторного чтения.
   Базовое ожидание для трёх ролей — 6 вызовов, 9 команд; не подменять этим
   сверку свежего контракта. Неясный ответ — STOP без повтора.
5. Проверить: пустые роли не получили исполнителя, задачи, расписание,
   расходы, изменённую личность, рабочий промпт или работающую модель.
   Катя и её рабочие настройки неизменны.
6. В конце этапа — один ZIP: JSON трёх анкет после записи вместе с отдельными
   штатными паспортами, карта, журнал revision/hash/UUID, список ID каталога,
   проверка «0 самоприёмок в отделе», тесты и что не проверено.
   Штатный паспорт не выдавать за перенос обязанностей в JSON анкеты.
   Приёмку за владельца не выполнять.

### Границы существующих инструментов

`update_role_passport` записывает отдельное штатное описание; это НЕ
автоматический перенос обязанностей в JSON исходной анкеты.
`update_employee_sections` умеет только разделы/связь с руководителем,
а `update_maria_profile` разрешён только Марии.

Владелец подтвердил: достаточно штатного паспорта и рабочего места, как у Hint.
Новый инструмент переноса обязанностей в JSON НЕ делать.

Обновление ссылок `personaRef`, книжки знаний и промпта в организационном
каталоге не входит в задание. Создание отдела повторно недопустимо.
Никаких изменений personaRef, книжки, промпта и рабочих настроек Кати.
