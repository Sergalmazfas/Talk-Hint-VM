# Постоянный TalkHint backend для отдельного мобильного клиента

Адрес опубликованного backend подтверждён через deployment metadata:
**https://talkhint.app**. В приложение передаётся origin без `/api`.

Эти изменения подготовлены в основном проекте. Они ещё не опубликованы:
владелец делает Publish после прохождения проверок. Файлы в отдельном новом
Replit-проекте автоматически НЕ обновляются из этого workspace.

## Постоянный сервер

- `/api/mobile-secretary/*` регистрируется и в production.
- Токены отдельные, hash-only, owner-scoped, с refresh/logout.
- Google browser handoff работает через существующий login/callback с
  явным разрешением мобильному клиенту, не предоставляет права `/admin`.
- Production хранит scoped sessions/reviews/TEST в новой additive-таблице
  `mobile_secretary_state`, создаваемой при первом обращении. Старые Dev данные
  остаются в `mobile_secretary_dev`. Реальные звонки остаются в прежних
  `secretary_tasks` и истории, без новой параллельной CRM.
- Очистка технических данных через 24 часа — продолжение прежнего технического
  механизма, не утверждение срока хранения истории звонков.
- Существующий TEST API сохранён и не начинает звонки даже в production.
- Live использует тот же `secretaryBackend(dialSecretaryTask)`, что ChatGPT.
  Провайдер строго OpenAI; выбранные model/voice не подменяются.
- Подключение приложения не назначает номера и не включает входящий AI.
- SMS, согласия на запись, callback-проверки и остальные ограничения не изменены.
- Privacy/Terms не объявлены утверждёнными; новых legal approvals не создаётся.

## Контракт для уже созданного мобильного проекта

1. Настрой `EXPO_PUBLIC_API_ORIGIN=https://talkhint.app`.
2. Удали прежний запрет этого домена в `src/config.ts`.
3. GET `/api/mobile-secretary/me`: сервер возвращает
   `callingMode:"live", testOnly:false` в production. До обнаружения этой
   capability оставайся в TEST; не выбирай live только по названию домена.
4. При live: POST `/api/mobile-secretary/live/prepare` с существующим телом:

```json
{
  "clientRequestId": "сохранённый UUID поручения",
  "recipient": "получатель",
  "phoneNumber": "+1…",
  "instruction": "точное поручение",
  "cardIds": []
}
```

5. Ответ — immutable review с ID `live:…`, `testOnly:false`, номером,
   поручением и snapshot выбранных собственных карточек. Покажи review и
   честное предупреждение, что подтверждение начнёт реальный звонок.
6. Только после явного нажатия владельца:
   POST `/api/mobile-secretary/live-reviews/{encodeURIComponent(id)}/confirm`
   с `{"confirmRealCall":true}`. Пустое тело не является разрешением.
7. Для восстановления/статуса/результата: GET
   `/api/mobile-secretary/live-reviews/{encodeURIComponent(id)}`.
   Список: GET `/api/mobile-secretary/live-reviews`.
   Сохраняй тот же review ID; опрашивай состояние, не вызывай prepare/start
   автоматически при timeout/restart. Если есть `warning`, покажи его.
8. До запуска можно отменить review:
   POST `/api/mobile-secretary/live-reviews/{encodeURIComponent(id)}/cancel`
   с `{}`. Это не завершение уже активного звонка.
9. Старые ID без префикса `live:` остаются `/test-tasks/*`. Никогда не превращай
   сохранённую TEST-задачу в реальный звонок.
10. Live badges/тексты должны говорить CALL/LIVE, не «No calls are placed».

Контекст ограничен существующим безопасным лимитом engine на поручение:
длинные карточки требуют сокращения до подтверждения; текст не обрезается молча.
Карточки берутся только из явно выбранных собственных; неявных shared/private
подстановок нет. Их содержимое передаётся как сведения, не переопределение
системных правил.

## Защита повторов

Сначала SQL prepared→starting для review с привязкой к владельцу. Только
победивший запрос вызывает engine. Engine также использует исходный UUID
и существующую durable lease. При timeout или потере acknowledgement
повторное подтверждение только находит ранее созданную задачу. Если результат
неясен, сохраняется starting с предупреждением; автоматического redial нет.
Crash после lease, но до engine start может оставить неопределённое состояние:
безопасность от дубля важнее автоматического повторного звонка.

## Что сделать владельцу

1. Publish основного проекта после отчёта о проверках.
2. Обновить уже созданный отдельный мобильный проект по контракту выше или
   применить patch клиентских файлов из этого workspace, предварительно
   сверив отличия с текущим кодом нового проекта.
3. Перезапустить Metro/пересобрать клиент после смены EXPO_PUBLIC_API_ORIGIN.
4. Войти в прежний аккаунт и проверить реальный review. Звонок начинается
   только после отдельного подтверждения владельца в приложении.

Не импортировать backend в мобильный проект. Никаких новых ключей Twilio/OpenAI
в приложение. EAS/Apple signing и нативная установка остаются отдельными от
публикации backend. Агент не делает реальные звонки для этой проверки.

## Проверка browser approval — 23 октября 2026

Постоянный backend уже доступен: `/api/mobile-secretary/me` без токена
возвращает 401, а страница Google-входа доступна. Это уточняет исторический
статус «ещё не опубликованы» выше, но не доказывает signed-in native путь.

В локальном Chromium воспроизведён сбой POST
`/api/mobile-secretary/browser/approve-form`: заголовок страницы
`Referrer-Policy: no-referrer` заставляет HTML-форму отправить `Origin: null`,
и строгая проверка Origin правильно отвечает 403.

Точечная правка в backend задаёт **только странице формы разрешения**
`Referrer-Policy: strict-origin`. Теперь браузер отправляет исходный Origin,
а Referer содержит только origin, без approval id из query string.
Проверка Origin, авторизация владельца и одноразовый verifier не отключены.
API сохраняет прежний `no-referrer`; сторонние Origin по-прежнему запрещены.

Проверено в тестах с синтетическим владельцем, без Google-аккаунта и БД:
реальная HTML-форма в Chromium (403 до правки, 200 после), запрет отсутствующего,
`null`, чужого и неверного по схеме Origin; явное разрешение; неверный verifier;
однократная выдача scoped-токена. Проверки мобильного backend и browser transport:
35 passed; `npm run check`: passed. Dev-сервер перезапущен, гостевая страница
входа визуально доступна.

**Эта правка ещё не опубликована.** В этом workspace нет доступа к файлам
отдельного проекта и физическим устройствам. Владелец указал расположение
актуального клиента: `artifacts/talkhint-secretary-mobile` в существующем
отдельном мобильном проекте. Не заменять его автоматически копией
`apps/secretary-mobile`.

После попадания правки в постоянный backend остаётся проверить отдельно на
iPhone и Android: системный Google browser handoff, явное разрешение и возврат,
SecureStore после закрытия/перезапуска, refresh с отзывом старого токена,
logout и повторный запуск без восстановления отозванной сессии.
Эти результаты не заявлены проверенными. Звонки, SMS/push, платные сборки
и изменения провайдеров для этой проверки не выполнялись.
