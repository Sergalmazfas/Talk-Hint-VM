---
name: Large model verification boundaries
description: Why migration verification must be bounded and independent from active Hint.
---

Не держать одновременно исходную развёрнутую историю, полную проекцию
и выгрузку всех нормализованных строк. Хеширование — без клонирования
полного JSON, проверка — порциями; технический импорт запускается отдельно
от web/Hint worker.

**Why:** активный упакованный JSON существенно меньше развёрнутой истории.
Первая полная проверка исчерпала Node heap; транзакция откатилась. Это не
основание останавливать Hint или молча повышать память рабочего процесса.

Восстановление по техническим указателям не делать полиморфным SQL-join
с преобразованием составных PK в строки на свежезагруженных таблицах.
Использовать ограниченное чтение и индекс одной таблицы за раз.

**Why:** при массовом импорте без устойчивой статистики такой join дал
катастрофическое число чтений индекса, хотя маленькие fixtures проходили.
Малый тест не доказывает приемлемое поведение на полном снимке.

**How to apply:** каждое переключение источника требует проверки полного
снимка и его хеша, отдельно от малых тестов. Наличие импортированных строк
и успешный тест не позволяют отметить cutover/production зелёным.

Приёмка переноса отдельно проверяет стоимость последующих записей:
обычная правка должна записывать и проверять только изменённые данные,
не копировать весь снимок или граф при каждой новой ревизии.

**Why:** владелец принял точность теневого переноса, но запретил включение
и Publish из-за усиления записи, которого не обнаружили малые fixtures.
Успешное обратное восстановление не доказывает устойчивость хранилища.

**How to apply:** до допуска к включению нужен проход последовательных
разнотипных правок на полной изолированной копии с фактическими строками,
байтами и временем каждой записи и проверкой истории после каждой.
Оценку числа оставшихся правок не выдавать за измеренный лимит PostgreSQL.

Исторический декодер должен использовать зафиксированный контракт полей,
а не выводить его заново из текущей схемы PostgreSQL. Правила нормализации
нельзя менять под прежним номером контракта; старый декодер сохраняется.

**Why:** адреса неизменяемых записей зависят от точного набора полей и
правил кодирования. Даже добавление колонки в исходную схему может сделать
старые контрольные суммы нечитаемыми, если выводить формат динамически.

**How to apply:** изменения формата требуют новой версии и проверки всех
исторических чтений. Структурный digest хранилища не подменяет семантический
SHA полного JSON или побайтовый SHA текста документа.

Полноразмерные проверочные копии этой миграции сохранять до ручной проверки
владельцем. Удаление — только по отдельному разрешению и точному списку.
Малые fixtures очищают только собственные явно выделенные строки.

**Why:** владелец требует видеть нагрузочную копию после прогона и не
разрешает использовать принятый shadow как изменяемый стенд.

**How to apply:** в пакете указывать метку, идентификатор и инвентарь копии;
не включать её в автоматическую очистку тестов.

Нагрузочная проверка однородных записей не заменяет проверку смешанных
пакетов: изменение старой записи + добавление новой, удаление + добавление,
несколько изменений той же записи. Прямой reader проверяют и у изменённого,
и у нового документа.

**Why:** разбор изменений только по длине массива может сохранить добавление,
но потерять редактирование; корректный JSON книги сам по себе не доказывает
правильность отдельного индекса документа.

**How to apply:** сравнивать весь сохранённый JSON с последовательным старым
доменным движком, а затем независимо читать документы и предыдущую ревизию.
Замеры финального writer повторять после исправления таких веток.

Пустой Publish schema diff не доказывает полного совпадения ограничений:
на фактической сверке он не отразил различия DEFERRABLE/INITIALLY DEFERRED
у внешних ключей. Проверять определения pg_constraint и индексов отдельно.

**Why:** только сравнение каталогов обнаружило различие поведения FK,
хотя перечень таблиц, колонок и обычный schema diff выглядели одинаково.

**How to apply:** в пакете показывать digest фактической структуры и явные
отличия; не подменять их зелёным статусом стандартного diff. Не исправлять
managed production собственным DDL-скриптом.

Ограничения транспорта проверять по настоящему архиву, а не активной модели:
историческая запись может быть десятки мегабайт, весь NDJSON — больше гигабайта.
Gzip уменьшает передачу, но не размер строки после распаковки.

**Why:** полный архив оказался больше ограничений малого синтетического
обработчика, хотя независимое чтение модели и документов проходило.

**How to apply:** фиксировать максимум строки и общий объём до разрешения
импорта; парсить сегментами без квадратичного копирования. Полное декодирование
и проверку истории выполнять отдельным ограниченным процессом с резервом
памяти для Hint, не внутри его event loop.

Перед выдачей полного пакета проверять лимит доставки: Library отказалась
регистрировать ZIP больше 100 МиБ. Не заменять реальный payload «образцом».

**Why:** gzip полного архива сам превысил лимит вложения.

**How to apply:** сохранить полный поток и его SHA, использовать lossless
контейнер с большим словарём, проверять распакованный поток по частям.
В README явно указать формат и не читать гигабайтную запись ZIP целиком в RAM.

Для приёмки запечатанного пакета требуется отдельная обратная сборка
именно скачанного объекта, а не повторная ссылка на проверку encoder до экспорта.

**Why:** владелец отдельно потребовал доказать восстановление из доставленного
пакета; совпадение SHA потока само по себе не проверяет SQL-backed decoder.

**How to apply:** изолированная транзакция Dev с ROLLBACK, сверка полного
semantic SHA с настоящим B, прямых документов/UTF-8 SHA и архивных payload.
Не вызывать production-import handler или выдавать grant ради этой проверки.
