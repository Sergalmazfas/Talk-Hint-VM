name: Chat action boundaries
description: Owner-approved universal action-first chat, route evidence and user-versus-Crew result boundaries.
---

Чат должен работать по действию (купить / узнать / записаться / договориться),
а не требовать выбора профессии. Максимум 2–3 недостающих ключевых вопроса;
известное не переспрашивать. Подготовленная карточка не даёт права звонить:
согласование карточки → прежняя проверка → отдельный Start владельцем.

**Why:** владелец потребовал универсального помощника, а не отдельную архитектуру
про шины или повторную анкету. Решение дано для Dev с проверкой Клавдием и
отдельным Publish владельцем.

**How to apply:** сохранять условия/запреты и исправления без усечения. Отсутствие
цен/наличия не заменять выдумкой; при отказе от геолокации спросить город.

Поиск Google Maps выбран владельцем. Route bias и геометрическое расстояние
не доказывают автомобильный detour, доступ со съезда или «только у трассы».

**Why:** требование «только у трассы» существенно для поручения; выдача обычного
route-biased результата за соответствие нарушила бы его условия.

**How to apply:** явно отмечать непроверенное; не заявлять полноценную проверку
Maps по наличию Secret или offline-фикстуре.

Пользовательский итог звонка и Crew-разбор — разные сообщения с разными
источниками. Разбор команды, нормы и лаборатория — только owner/admin.
Follow-up в переписке не равен календарному событию/напоминанию.

**Why:** владелец разрешил обычному клиенту только итоги своих задач, сохранил
Gmail и отдельно запросил краткий внутренний разбор в том же чате.

**How to apply:** проверять приватность на сервере и в контексте модели, не
только в меню; не включать агентов ради доставки уже сохранённого результата.
