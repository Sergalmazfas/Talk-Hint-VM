---
name: MCP atomic storage boundaries
description: Composite MCP operations must be checked against real repository limits, not only in-memory repositories.
---

Составную MCP-операцию проверять через ограничения настоящего репозитория,
включая входной адаптер и активное хранилище. Успешная генерация команд
и тестовый in-memory repository не доказывают возможность сохранения.

**Why:** операция создания отдела проходила тесты на подменённом хранилище,
но реальный входной репозиторий отвергал размер атомарного пакета ещё
до обращения к базе.

**How to apply:** отдельно проверять полный пакет вместе с квитанцией,
границы размера и отказ без частичного сохранения. Не обходить отказ
разбиением структуры на несогласованные записи и не расширять общий
доступ к массовым изменениям ради одной узкой операции.

Проверка количества команд не заменяет проверку нормализованной проекции
согласованного JSON.

**Why:** пакет может пройти настоящий ограничитель размера, а затем упасть
на несовместимости формы анкеты с проектором; in-memory репозиторий этого
не замечает.

**How to apply:** отдельно проверять проекцию исходного шаблона и сохранность
его содержимого. Не выдумывать характер или другие незаполненные сведения
ради требований хранилища; совместимость должна быть узкой и сохранять
строгость для остальных форматов.

При проверке результата нельзя ожидать `revisionBefore + 1` на каждый
MCP-вызов: один атомарный пакет содержит несколько команд хранилища,
включая служебную квитанцию.

**Why:** успешный пакет создал документ правила, сохранил паспорт и квитанцию;
локальная проверка ошибочно остановилась, ожидая одну ревизию вместо трёх.
Повторное чтение подтвердило сохранность прежних данных.

**How to apply:** до записи определить ожидаемое число команд пакета,
затем сверить подтверждённую revision с этим планом и revision повторного чтения.
Не заменять точную проверку простым условием «revision выросла».
Не считать наличие квитанции общим свойством всех write-tools: проследить
конкретную ветку сборки команды, а не переносить число команд с соседнего инструмента.
**Why:** успешная одиночная запись была ошибочно остановлена локальной
проверкой, которая ожидала отдельную квитанцию по образцу другого инструмента.
После уже объявленного STOP не продолжать записи без нового решения владельца,
даже если выяснено, что ошиблась локальная проверка; успешную запись не повторять.

Для последовательных production-фаз держать одного активного writer.
Следующую фазу запускать после уведомления об окончании фоновой задачи и
проверки журнала, а не по `pgrep`/отсутствию PID.

**Why:** в этой среде проверка PID не увидела ещё работающую фоновую задачу;
предохранитель следующей фазы сработал до её готовности, не отправив запросов
в production. Отсутствие видимого процесса не доказало завершение.

**How to apply:** жизненный цикл фоновых задач сверять по их идентификаторам
инструмента, а журнал — по последней подтверждённой записи.
Локальное «предыдущая фаза ещё не готова» не смешивать с расхождением
production или неоднозначным ответом на запись.
