Решение владельца 28.10.2026: переносить данные на целевую инфраструктуру
сейчас, с расчётом на рост компании. Всё в Replit, без новых аккаунтов;
мощность сервера владелец наращивает сам.

Цель: нормализованные PostgreSQL-таблицы ролей, действий, связей, документов
и версий, журнала, звонков, отчётов и решений; pgvector в той же базе для
памяти команды; Replit Object Storage для больших файлов, в базе ссылки
и digest; очередь агентов в PostgreSQL. Dev и production раздельные.
Ежедневные резервные копии с проверкой восстановления; P.OPS наблюдает
ёмкость, ошибки записи и свежесть копии.

Прежние стабильные ID, web-книга, get_document и JSON-экспорт сохраняются.
Старый JSON после переключения источника — архив только для чтения;
история не удаляется. Работа лаборатории Hint не должна прерываться.

Дополнение владельца к приёмке схемы: профиль сотрудника (имя, три черты,
девиз, портрет/файл, цвет, выбор владельца), версии промпта и принадлежность
роли к режиму — явные таблицы/колонки, не extra_fields. Два уровня продукта
по режимам пока не активировать: схема должна их поддержать, не перестраивая роли.

Production-механизм принят: после Publish №1 owner-authenticated import
переносит модель компании как единственный источник истины; лаборатория
читает журнал из production. Привязку Dev/production аккаунтов владелец
подтверждает отдельно при переносе; совпадение ID не предполагать.
В пакете B требуется распределение extra_fields по разделам и рекомендации
по переводу в явные поля.

**Why:** прямое решение владельца; не очередное расширение монолита как
постоянная архитектура и не создание параллельного каталога.

**How to apply:** весь фокус — переезд до конца; промпты P.LAB/P.LG.QA,
экран «Команда» и новые роли на паузе до его завершения. Уточнённые контрольные
точки владельца: A — окончательный DDL, полный инвентарь, план импорта/сверки,
без «да» переноса нет; B — этапы 1+2 в Dev, сверки и shadow-read, «да»,
Publish №1 владельцем, перенос production по согласованному механизму и проверка;
C — файлы/pgvector (3+4), пакет, «да», Publish №2; D — изоляция, ежедневные
копии с реальным восстановлением и P.OPS (5–7), пакет, «да», Publish №3;
E — итоговый акт переноса, восстановления и наблюдения.
Каждый пакет — один ZIP с README «что проверено и как».
Расходы не считать и Usage не запрашивать — владелец исключил это из работы.
Согласование направления не разрешает автоматическое включение агентов,
провайдеров или публикацию. Hint не трогать и не останавливать.

Дополнительный барьер владельца перед включением новой базы основным
источником: ответ `updateMany` после правки — без полного чтения модели.
Это условие включения, не условие самого Publish. Время правки ролей
держать под наблюдением.

**Why:** владелец разделил выпуск схемы, привязку аккаунтов и реальный
импорт/включение; приёмка кандидата не отменяет этот барьер производительности.

**How to apply:** до включения проверить путь ответа записи и сохранить
контракт клиентов. Предварительный Publish не считать разрешением импорта.

Теневой импорт не должен помещать старый JSON под рабочий ключ владельца:
даже без normalized-флага legacy-reader способен начать его выдавать.
Архивный родитель и история изолируются техническим ключом; отдельное
включение проверяет обе ветки маршрутизации, не только новый reader.

**Why:** согласование импорта и включения — разные контрольные точки;
FK-потребность архивов не должна незаметно включать данные через старый путь.

**How to apply:** проверять отсутствие новой legacy-записи живого владельца
после shadow-import и чтение книги/журнала до явного cutover. Если прежний
reader успел создать рабочую запись, не удалять её автоматически.

Владелец принял различия deferred-FK в неиспользуемом поколении B как есть:
не исправлять ради совпадения, B не активировать. Подтверждение пары
аккаунтов дано только для new-country, не для всей книги original и не
как разрешение импорта или переключения источника.

**Why:** явное решение владельца после независимой сверки.

**How to apply:** сохранять различия в отчёте, не выдавать пустой стандартный
diff за полное совпадение. Original может сохраняться техническим архивом;
его активация не входит в подтверждённый объём.

Владелец выбрал production Dedicated 2 vCPU / 8 GiB; смену машины делает сам
вместе с согласованной публикацией, в тихое время без звонков. Это решение
о будущей конфигурации, не доказательство уже сменившегося runtime.

Принятый исходник модели Dev заморожен до переключения: роли, лаборатория
и исполнитель не меняют модель. Неизбежная правка требует нового пакета
и независимой сверки. Отложенное дополнение журнала применяется в production
после отдельного включения источника, а не в замороженном Dev.

**Why:** владелец разделил сверку кода, разрешение точного манифеста,
вписывание approval, смену машины/Publish, кнопку импорта и включение;
ни один шаг автоматически не разрешает следующий.

**How to apply:** проверять фактический источник и ревизию перед пакетом;
не считать доступный объём RAM гарантией свободной памяти. Production-замеры
и готовность новой машины подтверждать после её реального запуска.
