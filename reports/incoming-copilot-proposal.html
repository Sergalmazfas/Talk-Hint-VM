Входящий Copilot: «Обо мне» + текущий разговор

Рекомендация: развивать существующий My Context, а не создавать второй Brain или новую базу профилей. Профиль и причина звонка необязательны. Пользователь говорит сам; TalkHint предлагает следующую полезную реплику.

Граница достоверности. Выводы получены чтением текущего кода после изменений #305. В этой задаче не запускались модель, звонки, БД или workflows; не менялись приложение, prompt, UI, настройки и production. Единственный результат — этот документ. Иллюстрации ниже придуманы для согласования поведения, не являются результатами live-модели или фактами о пользователе. Код не доказывает версию установленного iOS-приложения или фактический production-путь.

1. Текущий путь и минимальный разрыв

  1. Определение владельца. Для входящего на назначенный номер server/routes.ts:1291–1325 ищет phoneNumbers по To и получает userId. Затем создаётся pending call с этим владельцем (:1375–1395). Неназначенная линия пула получает сообщение и завершение, а не персональный Copilot (:1454–1468).
  2. Принятие. /api/call/accept проверяет запись одновременно по callSid и авторизованному userId и вызывает setCallOwner (server/routes.ts:902–929). Hold-путь accepted включает stream на caller leg с обоими tracks (:1001–1026); iOS соединяется через конференцию (:1027–1048), browser через client:user-id (:1052–1071). Проверка присоединения iOS-конференции привязана к владельцу pending call (:1327–1368).
  3. Загрузка перед первой подсказкой. На stream start владелец берётся из callOwners, при отсутствии — из pendingCalls. Профиль сбрасывается и загружается один раз для звонка (server/websocket.ts:2516–2574). Guest-путь ожидает ownerContextReady и остальные блоки (:1731–1738). Ошибка загрузки оставляет пустой контекст; это не гарантия видимого сообщения об ошибке пользователю.
  4. Сборка. Затем автоматически загружаются CONTACT_CONTEXT по владельцу и номеру собеседника и все доступные ему cards (server/websocket.ts:2577–2620). server/contactMemory.ts:115–124: USER_CONTEXT → CONTACT_CONTEXT → STATIC_CARDS → подтверждённая TUTOR_MEMORY. Cards ограничены 1200 символами, обрезаются целыми карточками по приоритету, не по теме разговора (:147,188–212). Входящие используют fromNumber для памяти контакта (:42–47).

Forwarding — не подтверждённый отдельный путь Copilot. Настройка forwardingPhone и callMode существует (server/routes.ts:1973–2002,2949,3217), но в просмотренном обычном входящем handler не найдено ветвления, которое набирает forwardingPhone и одновременно подключает персональные подсказки. Там номер используется для SMS-уведомления (:1423–1438), а accepted-путь выбирает iOS/browser. Поэтому нельзя обещать подсказки при переадресации на обычный телефон по одному наличию настройки. Внешняя/операторская переадресация и другие развёрнутые маршруты не проверены; это отдельный продуктовый вопрос.

Пустой Goal допустим, но не равен гарантированно чистому входящему. goalsByUser хранит цель по пользователю (server/websocket.ts:894–906); обычная генерация берёт её без разделения по direction (:1834). shared/prompts.ts:395–398,425–427 подставляет generic “Have a successful conversation”; после #305 правила прямо разрешают отсутствие Goal (:51). Однако iOS повторно отправляет непустой сохранённый callGoal при подключении сокета (ios/TalkHint/Calls/CallHintStream.swift:246–254). Web сбрасывает цель в resetCallUI (talkhint/ui/script.js:1524–1535). Риск восстановления старого исходящего намерения на входящем — вывод из кода, не воспроизведённый инцидент.

Остаточный перекос. Общий LIVE prompt всё ещё содержит «professional salesperson / conversion», обязательное завершение переговоров и sales-примеры (shared/prompts.ts:85–106,187–194). Для персональных входящих требуется согласовать нейтральную применимость этих правил по теме и намерению Owner, а не создавать второй prompt по direction.

Изоляция: основания есть, абсолютной гарантии исследования нет

Профиль читается по userId (server/storage.ts:510–518); contact memory — по userId + phone (:891–898); cards — по userId (:1010–1017). Сокеты связаны с авторизованным владельцем, callOwners сопоставляет callSid → userId (server/websocket.ts:551–565). Но model/mode/language остаются module-global (:193,548–549), а цель — по пользователю, не по каждому его параллельному звонку. Это ограничения настроек/параллельности, не доказательство утечки биографии. Нужны отдельные проверки двух владельцев, неизвестного владельца и reconnect; существующие задачи по privacy cards не дублировать.

2. Один простой экран «Обо мне»

Уже есть: один текст users.userContext (shared/schema.ts:12), GET/POST /api/user/context с auth (server/routes.ts:2089–2113), iOS-редактор с шаблонами и Save (ios/TalkHint/UI/AssistantViewController.swift:201–322), клиент API (ios/TalkHint/Networking/APIClient.swift:468–487), web-modal (talkhint/ui/index.html:1207, talkhint/ui/script.js:2990–3100). Upload резюме и отдельное voice-to-profile в этих путях не подключены.

Предлагаемая спецификация, не готовый UI: заголовок «Обо мне»; пояснение «Необязательно. Помогает подбирать реплики, но не даёт разрешения сообщать ваши данные звонящему»; одно редактируемое поле со счётчиком до 4000; подсказки рядом: кто вы, профессия/занятия, уместные в общении сведения, желаемая простота английских фраз и язык помощи. Это направления для текста, не новые обязательные поля и не анкета перед ответом на звонок.

  • Действия: «Сохранить», «Отменить», «Очистить профиль» с подтверждением. Пустой профиль разрешён. Старый текст остаётся при ошибке сохранения; загрузочную ошибку не показывать как «профиль пуст».
  • «Загрузить резюме» — только после согласования импорта; результат открывается в этом же редакторе как черновик. Не перезаписывать сохранённый текст до подтверждения; при существующем тексте явно выбирать замену или ручное объединение.
  • Шаблоны — примеры, не факты: выбор/загрузка не сохраняют автоматически биографию. Не предзаполнять пользовательский профиль обсуждавшимися примерами профессий.
  • Уровень языка влияет на сложность реплик; язык перевода остаётся существующей настройкой. Не менять его молча из текста резюме. Профиль не выбирает текущую доступность.

Лимит сейчас незаметно обрезает данные: storage выполняет slice(0,4000) (server/storage.ts:21,515–518), iOS — prefix при вводе и сохранении (AssistantViewController.swift:294–296,316–321), POST проверяет тип, но не отклоняет превышение. В web поле нет maxlength в просмотренной разметке. Для предлагаемого экрана и импорта нужен явный отказ сохранить превышение, сохранение полного черновика и подсказка сократить. Согласовать одинаковый подсчёт Unicode на Swift/JS; визуальные символы Swift и UTF-16 длина JS сейчас различаются.

Удаление. Очистка сохраняет пустую строку через существующий API (storage хранит null). Она не удаляет независимые контактные summaries, cards, транскрипты или уже загруженный в активный звонок snapshot. Показывать это прямо; рекомендуемое применение профиля — со следующего звонка. Не обещать «забыть всё». Доступные Contacts остаются отдельным местом редактирования/удаления памяти.

3. Три способа ввода — поэтапно

СпособСтатус и предложение
ТекстУже работает. Переиспользовать поле, API и userContext; исправление прозрачности лимита/ошибок согласовать как минимальную доработку.
РезюмеНовая функция. Минимум на согласование: UTF-8 TXT и PDF с текстовым слоем. DOCX — отдельное решение по спросу; не обещать DOC/сканы/OCR. Извлечение текста локальным серверным парсером без генерации новых фактов; API возвращает черновик, не сохраняет профиль.
ГолосНеобязательный поздний этап вне звонка: диктовка → текст → проверка → Save. PREPARE уже имеет запись и /api/prepare/stt (ios/TalkHint/UI/PrepareViewController.swift:12–16,467–500), но активирует цель, не профиль. Не подключать его напрямую к userContext; возможное повторное использование только записи/STT после отдельного согласования.

Импорт: выбрать файл → проверить формат/размер → извлечь → показать весь доступный текст и ошибки → пользователь убирает лишнее и чувствительное → явное подтверждение → существующий POST. Если текст больше 4000, он остаётся черновиком, Save заблокирован с понятной причиной; никакого молчаливого усечения или автоматического AI-резюме. При нарушении технического лимита извлечения честно отказать, не представлять частичный результат как полный.

Обработать повреждённый/защищённый PDF, пустой текст или скан, неверный тип/MIME, недопустимую кодировку, превышение размера/страниц, таймаут, отсутствие сети и ошибку сохранения. Дать повторить или вставить текст вручную. До загрузки показать предупреждение убрать SSN, номера документов и чужие контакты; извлечённый файл — данные, а не инструкции Brain.

Рекомендуемое хранение: исходные файлы не сохранять постоянно, временные данные удалять после обработки/ошибки/таймаута; не писать содержимое в логи. Сохранять только подтверждённый текст в существующем поле. Предлагаемый стартовый технический предел для обсуждения: 5 МБ и 10 страниц, отдельно от лимита профиля 4000. Итоговые форматы, пределы и политика обработки требуют согласования.

4. Одна политика Copilot

Owner Profile + необязательный Reason for Call + Live Conversation + последние явные слова Owner → следующая полезная реплика. Это смысловые роли существующих данных, не новые сущности и не массовое переименование Goal.

  • Текущий вопрос обрабатывается в контексте разговора; свежие явные слова Owner важнее устаревших изменяемых фактов биографии. Предложение Guest обновляет ситуацию, но не становится согласием Owner и не снимает его обязательных ограничений.
  • Профессия водителя не навязывается врачу; сведения о другой деятельности используются только когда разговор к ней относится. CONTACT_CONTEXT — история, не проверка личности звонящего; совпадение номера само по себе не разрешает раскрытие данных.
  • Знать факт ≠ иметь право раскрыть его. Не пересказывать резюме неизвестному собеседнику, не раскрывать чувствительные значения; существующие redaction/placeholder-ограничения сохраняются. При сомнительном запросе помогать уточнить цель/личность и выбрать безопасный канал, а не уверенно заполнять ответ из профиля.
  • Не выдумывать доступность, текущую работу/местоположение, наличие документа, симптомы или обещания. Неизвестный номер — естественная просьба дать время; известный уместный факт — короткий DIRECT.
  • При неизвестной доступности Wednesday/Friday — существующий CHOICE, затем Owner сам произносит ответ. Нажатие варианта не равно сказанному. Обычный trigger остаётся Guest final; без Owner-final генерации, private mic, voice commands, mute или автоматической речи AI.
  • Не объявлять любую продажу нежелательной. Если Owner явно отказался продолжать, помогать завершить без sales-pressure; если он заинтересован — поддерживать вопросы/обсуждение.

Граница cards/истории. Сейчас они подмешиваются автоматически, а headers советуют применять сведения бизнеса «with confidence» (server/contactMemory.ts:50–78). Предлагается сначала уточнить общую релевантность и границу раскрытия для всех источников, не удаляя cards и не отключая CONTACT_CONTEXT молча. Для личного пользователя пустых cards достаточно. Если потребуется исключать бизнес-карты из личных разговоров ещё до передачи модели, это отдельное согласуемое изменение выбора источников, а не подразумеваемая функция текущего MVP.

Все реплики — иллюстрации ожидаемого поведения, не модельные результаты. Входы ограничивать историей на соответствующий turn. Разделять проверки сборки/изоляции и реальные поведенческие ответы модели.

6. Минимальный план после согласования

  1. Уточнить контракт. Один профиль в userContext, не обязательный; никаких новых таблиц/поиска/автоматической долговременной памяти. Зафиксировать каналы, импорт и правила приватности.
  2. Улучшить существующий редактор. About Me copy, счётчик, явные ошибки/очистка и отсутствие silent trim: iOS AssistantViewController + APIClient; web index.html/script.js; routes.ts POST и storage.ts setUserContext. Проверять результат записи, не выдавать пустой fallback за успешное сохранение.
  3. Добавить только согласованный импорт. Тонкий авторизованный endpoint извлечения текста без записи профиля, ограниченный парсер и выбор файла в согласованных клиентах; существующий Save сохраняет подтверждённый текст. DOCX/OCR и голос не включать без отдельного решения.
  4. Минимально согласовать контекст. shared/prompts.ts и headers server/contactMemory.ts: релевантность, раскрытие и ограничения sales-политики. До правки провести аудит shared consumers. В CallHintStream.swift / websocket.ts отдельно определить срок жизни намерения, чтобы старый default не выдавался за повод нового входящего; без второй Brain-политики и нового trigger.
  5. Проверить матрицу. Сборка для пустого Goal, двух переводных настроек, выбора источников и изоляции; отдельно ограниченные реальные модельные проверки после разрешения. Не менять STT, модель, CHOICE/NO_HINT или баннер. Выпуск/контрольный звонок — только по отдельному согласию.

Решения, которые нужны от пользователя

  • Первый выпуск экрана/импорта: iOS, web или оба? Нужны ли подсказки именно при переадресации на обычный телефон, а не при принятии в приложении?
  • Подходит старт с TXT + текстовым PDF без OCR, DOCX позже? Подтвердить предел 5 МБ / 10 страниц либо другой; профиль остаётся 4000.
  • Импорт — извлечение с ручной правкой (рекомендуется) или отдельно согласованное AI-сокращение с просмотром изменений? Как показывать замену существующего текста?
  • Принимать ли применение сохранённого профиля только со следующего звонка? Какой default Goal должен действовать на входящем: никакой, если Owner явно не задал намерение для этого разговора (рекомендация)?
  • Достаточно ли контекстного запрета неуместного раскрытия, или нужны явные пользовательские ограничения по категориям? Последнее увеличит объём; не скрывать это за формулировкой «AI знает всё».

Итог: основу Profile + Conversation уже можно переиспользовать. Разрыв — понятный необязательный экран, безопасный подтверждаемый импорт, прозрачные лимиты/ошибки, срок жизни Goal и согласованная релевантность/приватность. В этом исследовании ничего из перечисленного не реализовано.
