Copilot V1: два перевода, обычный звонок

Решение: V1 — два независимых text-only Realtime-сеанса. Непрерывный Guest EN → RU получает копию outbound track родительской Owner-leg на новом изолированном Twilio Media Stream. Owner RU → EN получает PCM только при удержании private PTT через gate в единственном custom AudioDevice. Оригинальный Guest звучит как обычно; AI ничего не произносит и не советует.

Граница: только исходящий двухсторонний Copilot-звонок. Входящий caller-leg имеет зеркальные роли и остаётся будущим дизайном, а не заявленной поддержкой. Реализация ещё не одобрена.

                                                     └─→ RU→EN text-only ──→ owner feed

Copilot выбирается явным call mode на старте. Для него сервер выдаёт отдельный stream вместо Hint /twilio-stream; это не параллельный Hint и не существующий асимметричный Translator bridge. <Dial> остаётся нормальным voice path: отказ любого переводчика прекращает лишь соответствующий перевод, не голосовой звонок.

В звонке остаётся
  • Owner сам говорит Guest.
  • Guest playback слышен и в NORMAL, и в PRIVATE.
  • Обычные end/mute/speaker controls.
  • Никакой перестройки на press/release.
Не включается
  • twilioBridge.ts и Translator audio playback.
  • Hint, Flux/Terra/Brain, SAY/CHOOSE/NO_ACTION.
  • TTS, Secretary, автоответ или автоматически созданные spoken-label.
  • Remote-render tap: серверная Guest-копия делает его лишним.

2. Точный Guest source: parent outbound track

routes.ts:1496–1589 показывает исходящий owner/client leg: owner регистрируется по parent CallSid, затем <Start><Stream> идёт до обычного <Dial>. Для Copilot предлагается отдельная ветка:

<Start>
  <Stream url="wss://…/copilot-twilio-stream" track="outbound_track">
    <Parameter name="pairing" value="server-issued-one-time-nonce" />
  </Stream>
</Start>
<Dial …><Number statusCallbackEvent="answered completed" … /></Dial>

speakerRoles.ts:4–55 подтверждает семантику: на owner-leg исходящего outbound = Guest, inbound = Owner. Поэтому основной источник — outgoing-first server-side Guest copy: он не содержит private capture и не требует tap на playback iPhone. Но это не абсолютная speaker-purity гарантия: far-end echo может вернуть Owner, а stream, стартующий до <Dial>, может нести prompts/ringing audio.

Answer-bound filter обязателен. Сервер связывает stream start с parent CallSid, а child dial leg — с parent через новый подписанный Twilio status callback. Аудио до подтверждённого answered исключается; при completed/remote-ended обработка сразу прекращается и буферы очищаются. Существующий /twilio/dial-status — подписанный финальный parent callback, но сам по себе не доказывает момент ответа child leg.

Новый WSS нельзя просто добавить в публичный список websocket.ts:815–891: там user-auth применяется только к клиентским путям, а Twilio endpoints проходят отдельно. На HTTP upgrade новый endpoint проверяет X-Twilio-Signature по точному внешнему URL в канонической форме, требуемой Twilio для WebSocket handshake, с проверенной обработкой trusted proxy; угадывать схему по внутреннему request нельзя. После upgrade проверяются одноразовый server-issued pairing nonce, ожидаемый parent/account, срок и размер. Nonce передаётся через <Parameter>, не query string: Stream URL не поддерживает query parameters. Никакого доверия CallSid из сообщения без registry-binding. Raw SID/nonce/токены не отправляются в owner UI и не логируются.

Answer callback может прийти позже первых слов Guest. Безусловное отбрасывание всего до получения callback способно потерять приветствие. Предлагается краткий bounded staging buffer с привязкой к подтверждённому answer timing; если timestamp alignment не подтверждён, не выдавать полноту за доказанный факт и явно учитывать startup gap. Проверка первых слов входит в будущий smoke test. Копия μ-law mono 8 kHz преобразуется в PCM16 mono 24 kHz существующим codec pattern; upsampling не улучшает исходное телефонное качество.

Входящий звонок — не V1. На caller-leg роли зеркальны: inbound = Guest, outbound = Owner. Будущая поддержка должна отдельно выбрать stream leg и доказать mapping; V1 не переносит outgoing mapping на incoming автоматически.

3. Owner private gate: границы, а не UI mute

CallManager.swift:28–31,69–71 глобально устанавливает DefaultAudioDevice до звонков; SDK device нельзя безопасно заменить во время активного lifecycle. Минимальная будущая общая инфраструктура — один custom AudioDevice, установленный до calls: для не-Copilot режимов он работает как pass-through, для Copilot переключает capture destination. Это целевое поведение, не доказанная byte-for-byte эквивалентность DefaultAudioDevice: нужны сохранение echo cancellation/voice processing, проверка sample rate и регрессии. Guest original может акустически попадать в private microphone на speakerphone; разделение transports само по себе не устраняет это эхо. Это общая зона риска, поэтому «один screen flag» не даёт изоляции.

Press → PRIVATE-ready

  1. Запомнить native mute prior state и новый epoch/holdId. Gate переходит в PREPARING: реальные кадры уже не идут в Twilio, callbacks получают корректную тишину; Guest render не трогается.
  2. Audio callback подтверждает boundary/sample sequence. Одновременно отдельный text-only сеанс должен прислать применённый config/ready ACK; WebSocket open и нынешний session_config недостаточны.
  3. Только после обоих ACK UI показывает «Только Copilot». До этого пользователь не должен начинать приватную речь.
  4. В PRIVATE реальный PCM идёт только в owner translator; normal owner uplink остаётся muted. Перевод Guest продолжается независимо.

Release → безопасный NORMAL

  1. В capture callback закрыть private boundary с lastSeq; хвост до границы остаётся только переводчику.
  2. Очистить/разделить resampler и route buffers. Новые кадры разрешить Twilio только после подтверждённого reset; при неопределённом route — fail closed/видимый mute.
  3. Восстановить предыдущее native mute state, а не безусловно «unmute». Если пользователь был muted до PTT, он остаётся muted.
  4. Normal voice не ждёт финального текста. Перевод последнего private сегмента завершается асинхронно.
Ошибка никогда не открывает микрофон во время hold. Ошибка/таймаут/no-audio останавливает failing translator и показывает состояние, но не завершает voice call и не снимает gate. Только явный безопасный release/cancel с подтверждённым route restore возвращает prior mute state. Interruption, background, CallKit mute и Bluetooth route-change требуют того же fail-closed автомата.

4. Два directed text-only Realtime-сеанса

СеансВходВыход/UIЖизнь
GuestEN, outbound_track, только после answerRU text deltas → «Гость по-русски»Непрерывно до end/ошибки
Owner privateRU PCM только внутри hold boundariesEN text deltas → «Ваш перевод на английский»Подготовлен per-call; операции по hold

Переиспользуется provider boundary и OpenAI Realtime adapter, но нужны две фиксированные directed configs (sourceLangHint/outputLanguage/outputMode:"text"), не один смешанный bidirectional audio channel. В коде default — gpt-realtime (openaiRealtimeTranslator.ts:19), однако deploy/runtime override не исследован: default не выдаётся за production configuration. Native audio response запрещён; unexpected audio — fatal для этого translation session, не для звонка. Нет цепочки STT-final → Brain: source transcription служит корреляции/диагностике операции и может прийти позже текста.

Честное ограничение одновременности

Нынешний adapter использует server VAD с silence_duration_ms: 500 (openaiRealtimeTranslator.ts:271–300). Поэтому текст может появляться по готовности сегментов во время пауз, но длинная речь без паузы будет ждать её конца. Запрошенный перевод «до конца длинной реплики» существующим механизмом не доказан; одновременный перевод не гарантируется.

Перед реализацией нужно isolated-исследование source segmentation в том же provider: без новой модели, без скрытого STT→Brain и без silent provider switch. Для private release кандидат — ограниченный synthetic-silence tail, чтобы вызвать VAD; он не доказан. Не смешивать его с manual commit, иначе возможен двойной response. Альтернатива — manual commit/create ровно после release; она требует отдельного одобрения, потому что меняет UX на «текст после отпускания». Существующий 700 ms micro-turn gate нельзя переносить автоматически: короткие «да/нет» могут исчезнуть.

Один hold может породить несколько itemId/responseId; UI собирает их по source-item order внутри hold. Source transcript асинхронен и не задерживает открытие/streaming целевого текста. Пустой/no-audio hold не создаёт фразу; ошибка остаётся локальной переводчику.

5. Registry, транспорт и гонки

server call-mode registry (оперативный, TTL):
  opaqueCallId → ownerUser + COPILOT_OUTGOING + parentSid + childSid/answered/end
                 + one-time Twilio pairing + bounds + active epochs

copilot-private (session-auth owner):
  bind/ready: callId, epoch, direction=OWNER_RU_EN, applied text-only config
  press/audio/release: callId, epoch, direction, holdId, seq, lastSeq
  delta/done/error: callId, epoch, direction, holdId, itemId, responseId, seq

copilot-twilio-stream (Twilio-auth machine channel):
  start/media/stop + verified pairing; server adds callId, epoch,
  direction=GUEST_EN_RU, itemId/responseId/seq to owner-feed events

Registry создаётся только для явного Copilot mode, связан с authenticated owner и parent call до выдачи TwiML, принимает ровно ожидаемый account/call/nonce и уничтожается при terminal call status или call TTL. Epoch — отдельный для каждого направления: сбой Guest transport не сбрасывает Owner hold. Разрыв отдельного translation/feed transport закрывает его epoch, но не уничтожает активный телефонный звонок и не мешает reconnect. Owner feed — отдельный session-auth канал; ownership и активный call mode проверяются на bind и каждом reconnect. Item/response IDs в UI — непрозрачные app IDs с server-side mapping к provider IDs; секреты и raw Twilio identifiers клиенту не нужны.

Backpressure

Очередь аудио ограничена, например 1 секундой. При превышении — не молча queue/drop: послать явный gap, сбросить translation operation, увеличить epoch и пометить/закрыть partial. Не воспроизводить аудио повторно.

Reconnect

Поздние события старого epoch не обновляют текущую карточку. Допустим transient replay только последнего bounded text state; audio не replay. Guest reconnect не стирает private intent/result, а private reconnect не отменяет Guest translation.

Stale ≠ смысловое veto

Drop применяется по закрытым call/epoch/hold/response IDs. Новая Guest-реплика не делает намерение Owner недействительным и не удаляет его private перевод.

Lifecycle

Remote ended немедленно закрывает intake/provider/buffers. Translator disconnect не вызывает hangup. Duplicate release/stop идемпотентны; bounds действуют на frame, seq gap, hold duration и rate.

6. Минимальный экран

┌ Гость по-русски ───────────────────────────────┐
│ Они не смогут разгрузить вас до завтра…        │  streaming text
└────────────────────────────────────────────────┘
┌ Ваш перевод на английский ─────────────────────┐
│ I can’t wait until tomorrow…                   │  private hold result
└────────────────────────────────────────────────┘
       [ удерживать 🎙 Только Copilot ]   [mute] [speaker] [end]

Только описательные подписи направления, PTT/status и обычные call controls. Нет SAY, CHOOSE, advice, обязательного полного transcript, TTS и признака «Spoken»: показ/ACK/release не означает, что Owner произнёс фразу Guest.

«Скажи, что…» — нужен выбор

Strict translator может буквально перевести вводную. Рекомендуемый baseline: Owner диктует готовое сообщение — «Я не могу ждать…». Альтернатива после отдельного одобрения: ограниченное Copilot-only правило в том же Realtime translator, которое удаляет только распознанную вводную-команду и переводит её объект. Это не существующий default prompt, не дополнительный AI/Brain и не изменение production Translator prompts. До выбора UI должен обучать прямой диктовке, а не обещать command semantics.

7. Privacy и V2

OWNER_PRIVATE audio/text не попадает в call transcript, CRM, recordings, БД, analytics content, debug logs, cards, long-term memory или обычный Hint context. Guest translation также transient для экрана V1, если отдельное хранение не одобрено. Operational audio/text buffers ограничены call/hold/TTL и очищаются на close/error/end. В логах — только redacted IDs, state, counts и timings без содержания.

Аудио обрабатывает внешний Realtime provider. Документ не обещает provider zero retention: политика/настройки обработки и retention требуют отдельной проверки и пользовательского согласия. Любая запись или новое хранение — отдельное разрешение.

V2 — только качество контекста перевода, не Brain. Будущий bounded per-call role-tagged context может использовать фактически услышанные GUEST_SPOKEN/OWNER_SPOKEN для разрешения «that / it / the second one». OWNER_PRIVATE не считается услышанным Guest и не входит туда автоматически. Нет summarizer, выбора ответа, SAY/CHOOSE/NO_ACTION, советов, retrieval или долгой памяти. Состояния Heard / Private / Translated / Spoken различны.

8. Latency, проверки и уровень доказательств

Измерять четыре независимые цепочки с коррелированными monotonic clocks и IDs:

  • Guest: first eligible Guest audio / VAD boundary → first RU text delta → UI rendered.
  • Owner: first private audio / VAD boundary → first EN text delta → UI rendered.
  • Gate: press → audio-boundary + config-ready → PRIVATE-ready.
  • Release: last private sample → route reset → prior NORMAL/mute state restored.

Старые ≈300 ms и firstTranslatedAudio из mic spike — не iPhone text latency и не SLA. До исследования segmentation нет обещания «практически одновременно» или p95.

Часы iPhone, нашего сервера и provider нельзя напрямую вычитать друг из друга: внутри каждого процесса нужны monotonic durations, а end-to-end — client measurements/ACK и оценка синхронизации с погрешностью. Время server receipt события VAD не равно физическому концу произнесённой фразы.

Будущая проверка — не выполнена

Сначала автоматические unit/protocol tests: role+answer gate, forged signature/nonce, registry ownership/mode/TTL, seq/gap/backpressure, multi-item hold, stale epochs, reconnect text replay, no-audio/unexpected-audio isolation, prior-mute restore и route-reset fail-closed. Затем device regressions отдельно для non-Copilot pass-through, Hint и Translator. И лишь по отдельному разрешению — один consented реальный двухсторонний smoke call с Guest-side leakage check и отказом переводчика. Он подтверждает сценарий, но не p95 и не production SLA. Никакие leakage-тесты в рамках этого отчёта не запускались.

9. Минимальное предложение на следующее одобрение

  1. Только outgoing two-party Copilot mode; обычный <Dial> и Guest playback неизменны.
  2. Новый owner-leg outbound_track на /copilot-twilio-stream, Twilio upgrade signature + nonce registry + child-answer/end gate.
  3. Один глобальный custom AudioDevice с pass-through default и boundary-ACK private gate; отдельный session-auth /copilot-private.
  4. Два directed text-only Realtime-сеанса и transient owner feed; никакого Brain, TTS, bridge или persistence.
  5. Сначала protocol/device evidence; затем отдельно согласовать реализацию UI и один consented smoke call.
Блокеры одобрения: (1) выбрать baseline «диктуй готовую мысль» либо Copilot-only правило «скажи, что»; (2) принять VAD 500 ms с паузами или одобрить отдельное segmentation/release исследование; (3) подтвердить право менять общий AudioDevice и обязательный regression scope; (4) утвердить Twilio pairing/status-callback контракт и external provider privacy review. До этого кодировать V1 нельзя.
