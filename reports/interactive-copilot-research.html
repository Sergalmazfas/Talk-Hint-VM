Interactive Copilot: CHOOSE → SAY

Исследование текущего кода. 24 сентября 2026, UTC. Не реализация и не результаты модельного эксперимента.

Вывод: рекомендован гибридный путь. Для актуального простого выбора использовать уже готовый option.en; для собственного текста и сложного продолжения — один новый вызов генерации. Существующий CHOICE уже содержит английские фразы, но не содержит безопасного протокола приватного выбора. Поэтому это небольшое расширение клиента и сервера, а не только изменение кнопки.

ЗадержкаЛокальная смена карточки не ждёт модели; серверная фиксация асинхронна. До её подтверждения состояние предварительное.Сеть + очередь/генерация + доставка. Показывать ожидание и явную ошибку, без обещания фиксированных секунд.
Цена первого ответаТекущий payload уже включает варианты. Более длинные SAY для всех ветвей увеличат токены и риск усечения: текущий LIVE лимит 250, refine 150. Не увеличивать лимиты автоматически.Первый ответ не обязан описывать все сложные продолжения; дополнительная генерация оплачивается только при вводе.

Совместимость: существующие label/en/translation достаточны для текста простого локального SAY без переопределения их смысла. Они недостаточны для вопроса Copilot, Other, идентификации выбора, доставки и жизненного цикла. Эти данные нужны как дополнительные поля/события. Нельзя менять общий CHOICE en на выбранную ветку для всех клиентов до выбора; legacy compat остаётся каноническим.

Новый вопрос Copilot вроде «Когда вам удобно?» — отдельное поле, не использование nativeHelper не по назначению. Сейчас nativeHelper относится к user_input и не отрисовывается как вопрос CHOICE. Other/TYPE — отдельное действие интерфейса, а не фиктивная фраза, которую якобы нужно произнести. Расширение prompt для приватных вопросов — отдельная часть будущей реализации.

Ограничение мгновенного показа: клиент не может знать о реплике, которую сервер уже получил, а клиент ещё нет. Поэтому строгая гарантия актуальности требует серверного подтверждения до окончательного SAY (сетевой round-trip, но без модели). Рекомендация для первой версии: мгновенный предварительный показ с явным «проверяем актуальность», затем подтверждение/снятие; если предварительный текст считается нежелательным риском — показывать SAY только после подтверждения. Ни один вариант не может гарантировать отсутствие будущей новой речи.

3. Минимальная механика — предложение, не существующий API

  1. Одна активная карточка решения на звонок. Сервер выдаёт непрозрачные decisionId/optionId и revision контекста вместе с callSid и source utteranceId. Идентификаторы создаёт сервер, не модель. iOS сохраняет envelope; label — только отображение, не ключ выбора.
  2. Отдельное событие приватного ввода. Условное owner_input содержит requestId, callSid, decisionId, expectedRevision и ровно одно из optionId/customText. Для обычного свободного уточнения — явный тип refine с текущей revision. Не отправлять это как ask_ai: его Goal classifier не должен запускаться. Сервер получает userId из аутентифицированного соединения, проверяет владельца, активный звонок, допустимый вариант, размер ввода и лимит частоты.
  3. Подтверждение. Ответ связан с requestId: accepted, stale, invalid, unavailable/error. Для готовой ветки сервер берёт en из своего сохранённого валидированного варианта, не доверяет присланному клиентом SAY. Accepted сохраняет решение без вызова модели; собственный текст запускает refine с текущими контекстами и приватным вводом.
  4. Повторы и изменение выбора. Повтор того же requestId возвращает тот же результат; тот же id с другим содержимым отклоняется. Новый выбор имеет новый id и последовательность намерения; результат старой генерации не может перезаписать новый. Изменение выбора заменяет текущий ответ на вопрос, а не добавляет второй противоречащий факт.
  5. Актуальность. Новый Guest final, Owner final, изменение явных ограничений/Goal или замена decision инвалидируют старую revision. Во время новой interim речи блокировать tap локально и сигнализировать активность с сервера; при final — выдать новую revision даже если новой подсказки нет. Консервативное инвалидирование может быть чаще нужного, зато не требует дополнительного классификатора. При stale не переигрывать старый выбор автоматически: предложить актуальный вопрос, сохранить набранный текст для ручного повторного подтверждения.
  6. Асинхронная генерация. Проверять call identity + revision + последнюю последовательность ввода до и после await. Та же проверка нужна для автоматического результата Guest, чтобы он не перезаписал выбранный SAY. Использовать нынешнюю механику push/bookkeeping, но не буквально pushHint без новых проверок.
  7. Связь пропала / звонок закончился. Не очищать текст до accepted. Нет связи — показать несохранённый ввод и отключить финализацию локального SAY. При reconnect запросить актуальную карточку; повтор возможен только для того же звонка и requestId. Завершение/смена звонка очищает временное состояние, pending UI и ответы; событие без активного звонка явно отклоняется, не переходит в общий чат.

Разделение Selected / Suggested / Spoken

Selected — принятое сервером приватное решение по конкретному вопросу. Suggested — подготовленный или показанный текст. Spoken — реальная речь из STT, с обычными ограничениями распознавания. Tap/ACK не подтверждают речь, прочтение, согласие Guest или выполненное бронирование. Эвристический score не является доказательством.

Предлагается небольшой ограниченный per-call блок PRIVATE OWNER INPUT: вопрос, выбранное значение, происхождение, последовательность, пометка «не произнесено». Он поступает в обычный Brain и refine отдельно от истории речи. Выбор Tuesday остаётся контекстом этой записи, но не общим правилом «всегда свободен во вторник». Следующий вопрос о времени может использовать его, не предполагая, что Guest уже услышал дату. Поздняя явная речь Owner отменяет противоречащий выбор; при неоднозначности нельзя считать согласие установленным. Завершённые/заменённые решения помечаются неактивными, объём ограничен, на конец звонка всё удаляется.

Текущие prompt-правила «CHOICE hypothetical until actual speech» нужно аккуратно уточнить: выбранное значение допустимо как частный ввод владельца, но не как spoken transcript. Не подмешивать его в fullConversation, persisted transcript, CRM delivery, contact summarizer, профиль или ownerSaid. Логи новой функции должны хранить статусы/идентификаторы, не произвольный приватный текст. Sensitive data не собирать через Other; существующие placeholder/редакция сохраняются и применяются также к новому refine-выходу (нынешний refine не вызывает normalizeSuggestion).

Для Strategy Memory локальный показ нужно связать с серверным принятием и подтверждением отображения, не создавать два цикла из-за tap + echo. Статусы выбора хранить отдельно от эвристического branch selected. Новую tap→SAY задержку нельзя записывать как старую Guest speech→hint latency. Изменение всей аналитики не требуется: минимально отдельный request timing и честное отсутствие данных, если ACK не дошёл.

4. Пользовательские сценарии

Все тексты ниже — иллюстрации желаемого поведения, не ответы запущенной модели.

  • Tuesday / Thursday / Neither. Tuesday → “Tuesday works for me. What times are available?” Neither → “Neither day works for me. What other days are available?” Дата становится приватным предпочтением, не уже согласованной записью.
  • 9 AM / 2:30 PM. 2:30 → “2:30 works for me.” Не добавлять “Let’s book it”, если выбор времени ещё не означает разрешение подтвердить все условия.
  • Неизвестное удобное время. Copilot: «Когда вам удобно?» Morning / Afternoon / Type. Afternoon → “Tuesday afternoon would work best for me. What times are available?” Только если Tuesday уже установлен как актуальное предпочтение; иначе не дописывать день.
  • Other. Ввод “Friday afternoon” → новый Brain turn → “Friday afternoon would work better for me. Is that available?” Не утверждать, что Guest предложил этот вариант.
  • Бюджет. Other → 750 → “I’d like to keep it around $750.” Валюту брать из разговора; если неизвестна — не добавлять доллар автоматически. $500/$1,000 не выдавать за известные лимиты Owner.
  • Известный ответ. Если Owner уже подтвердил нужный факт, сразу DIRECT; не заставлять его повторно выбирать.

Интерфейс первой версии

Переиспользовать закреплённый баннер: явная подпись «Выберите для помощника», краткий вопрос, до трёх вариантов и отдельный «Свой ответ». После выбора — SAY с пометкой приватного выбора и возможностью изменить его. Текст вводится в существующее поле, но режим ввода явно связан с вопросом. Ошибка/ожидание видны рядом, речь по телефону продолжается.

Inline-вопрос в ленте лучше сохраняет историю решений, но требует жизненного цикла старых кнопок, прокрутки и большего UI-изменения. Для первой версии не рекомендуется полный чат и обязательная история SAY. Клавиатура не открывается на обычный tap; только на TYPE. Перевод OFF скрывает перевод SAY и native helper; обычные UI-надписи следуют языку приложения. Новые подписи должны покрывать существующие локализации iOS.

5. Согласуемый план первой реализации

  1. Добавить обратно совместимый envelope решения, отдельный owner_input и per-call controller: validation, revision, dedup, отмена и подтверждения. Legacy clients продолжают получать прежние подсказки; новое поведение включать только для клиента с поддержкой протокола.
  2. Переиспользовать готовый option.en для простого выбора. Добавить Other/TYPE, связывание вопроса и приватного состояния с обычной генерацией и refine, обход Goal classifier. Не менять модель/STT/провайдера автоматически; признать, что существующий refine использует OpenAI, а не всегда выбранный Gemini.
  3. Уточнить только необходимые LIVE/Ask правила для приватного ввода; не переписывать общие цели исходящих/входящих и Tutor. Один Brain-вызов на подходящий Guest turn сохраняется; новый вызов разрешён только по принятому сложному вводу Owner.
  4. Обновить iOS banner/input/decoder, состояния pending/accepted/stale/error, отмену и повтор. Добавить call/revision arbitration для поздних ответов; сохранить перевод OFF, чувствительные данные и управление аудио без изменений.
  5. Проверить протокол и UI без реальных звонков; затем отдельно согласовать поведенческую проверку и контрольный звонок/выпуск. Не публиковать автоматически.

Приёмочная матрица будущей реализации

  • Готовый Tuesday/time/Neither: правильный SAY, ноль дополнительных модельных вызовов, один принятый выбор, Goal неизменен.
  • TYPE/Other: один refine, ноль Goal classifier; правильный контекст вопроса, ошибки видны, повтор не дублирует вызов.
  • Новая Guest/Owner реплика до tap, после tap, во время await: stale не перезаписывает актуальную карточку; даже при отсутствии нового hint старые кнопки не активны.
  • Двойной tap, смена выбора, два устройства и reordered replies: последнее принятое намерение побеждает, старые результаты отбрасываются.
  • Disconnect/reconnect, поздний ACK, конец и новый звонок: ввод не теряется молча, отсутствует перенос состояния и общий-chat fallback.
  • Поддельные callSid/optionId, чужой пользователь, oversized input: отказ до модели/сохранения, отсутствие утечки.
  • Selected без речи: не попадает в transcript/CRM/contact memory, не повышает speech usage; реальная речь учитывается отдельно.
  • Known fact → DIRECT; обычный Guest-final работает; Owner-final только обновляет/инвалидирует, не запускает обычную генерацию. Автоматические hints OFF по-прежнему не вызывают модель; новая функция отключена явно при выключенном Live Hints, не переопределяя старый Ask.
  • Translation OFF: пустые переводы и native helper на обоих путях; sensitive input не отражается в подсказках/логах. Native UI проверяется на маленьком экране и с клавиатурой.
  • Legacy format/compat и существующие adaptive/strategy tests сохранены. iOS XCTest — на macOS/Xcode; проверить tap→send→ack→render интеграционно, не только decoder.

Риски и границы

Главные риски — гонки с новой речью, превращение выбранного в якобы сказанное, непреднамеренная замена Goal и потеря текста при отправке. Гибрид уменьшает задержку простых выборов, но не устраняет сетевую проверку актуальности. Нет оснований обещать конкретную скорость без измерений. Для первой версии не нужны новые таблицы, долговременная память, голосовые команды, TTS, mute или отдельный Brain.

Нужно согласовать перед реализацией: гибридный путь и один баннер вместо большого чата; предварительный локальный SAY с подтверждением либо только подтверждённый SAY. Рекомендован безопасный вариант: финальный SAY после серверного ACK, без повторного вызова модели для готовых вариантов.

Что проверено в этом исследовании

Проведено статическое чтение текущего кода и существующих тестов, сверены ветви tap/Ask/доставка/память и формат вариантов. Приложение, prompt, настройки, база, production и workflows не менялись. Модельные запросы, звонки, тестовые прогоны и публикация не выполнялись. Изменение рабочей области — только этот отчёт. Он не доказывает поведение ещё не реализованной функции.
